# Life OS 开发协作与交付约定

- 版本：v0.1；V16 定点修订：2026-10-18
- 形成日期：2026-10-14；前次更新：2026-10-15
- 类型：工程工作流程约定
- 权威：约束开发与 Review 流程，不覆盖已确认 PRD

## 1. V16 当前施工授权与边界（2026-10-18）

Owner 已允许 GPT-6.1 Sol 在核实 R2 基线后，开始 V16 本地 G0/G1 工程工作，包括创建本地施工分支、编写代码、添加合成 fixture、针对性测试和生成补丁。

该授权不等于批准某个尚未审查的数据库 DDL，不等于已经执行迁移，也不等于允许对真实用户数据进行试验。最新产品决定见 [V16 Owner 决策与实施交接](2026-10-V16-Owner-决策与实施交接.md)，实际代码与验证状态见 [当前开发状态](当前开发状态.md)。

未经 Owner 后续明确授权，不得直接 push、merge、rebase 远端、force-push、创建 PR、发布正式 APK、接入真实云 AI 或上传敏感账本，不得操作真实用户账本，也不得用真实财务数据进行迁移或恢复试验。

全部 40 项属于同一个 V16 产品版本；内部按 G0–G7 依赖推进。单个 Gate 通过不等于整个 V16 完成，不得擅自删减范围或另设延期版本。

## 2. 文档与分支分离

`life-os-docs` 是长期产品文档分支；Android 代码在独立施工分支。不得通过直接合并整个文档分支来更新代码分支。

每次有意义的代码修改，先读文档分支 `docs/life-os/` 中相关 PRD、统一架构、讨论记录和最新开发状态，遵循 [文档库 README](../README.md)的权威顺序。必须理解 Owner 使用方式、被拒绝方案和设计缘由；发生实质冲突时报告 Owner，不由代码 AI 擅自裁决。

讨论历史进入 `01-讨论记录`，调研进入 `02-调研`，产品决定进入 `03-产品需求`，架构审查进入 `04-统一架构`，交互规范进入 `05-界面与体验`，施工状态与流程进入 `06-路线图`。新增文件同时更新 [文档索引](../文档索引.md)，待决冲突更新 [待核对清单](../待核对清单.md)。

## 3. 模型策略与针对性研究

不默认将全部任务交给最高推理成本模型。复杂多文件实现、Review Fix、UI/业务施工、跨文件重构优先由 GPT-6.1 Sol 执行，推荐 High reasoning；模型选择按任务性质决定。

Astra 仅用于实际出现的高风险局部架构会诊，不再默认开启新一轮总体深度研究。适用问题包括：核心架构难以取舍、Finance Canonical 模型、Evidence/Reconciliation/Running Balance 复杂语义、高风险 Room migration、复杂 Compose 手势仲裁，以及主力模型连续两次未能正确解决的局部问题。

Astra 输出可执行约束与待决问题，不自动取得 Owner 决策权；Sol 按批准范围施工，不擅自缩减已选功能。优先复用已有研究与官方资料；仅在新 API、具体架构风险或证据不足时针对性补查。

更高 reasoning 不能替代 requirement checklist、diff audit、最小编译验证、静态检索、独立 code review、CI 或真机验收。未执行的验证不能因模型能力强而视为已验证。

## 4. 工程阶段与 Review

大型 Task 按阶段门禁执行。Phase 0 仍需先核对代码、需求、风险和验收标准，但它是施工任务内部的第一阶段，不应把已授权任务无限停留在重新写计划。

| 阶段 | 工作及交付 |
|---|---|
| Phase 0 — Context / Requirements | 此阶段只读，不改代码；核实真实基线，列出 Owner requirements matrix、已实现/未实现、预计修改位置、架构/schema 风险、验收标准和 blockers。完成后继续已授权施工。 |
| Phase 1 — Implementation Plan | 明确必要实施边界：逻辑 commit、owner/repository、数据流、state flow 及禁止修改区域；新增越权或实质冲突才另报 Owner。 |
| Phase 2 — Implementation | 在已授权范围和明确边界内执行本地施工。 |
| Phase 3 — Requirement Audit | 重新逐条阅读 Owner requirements，以 Requirement / Implemented / Evidence 矩阵复核，不以“总体完成”跳过具体需求。 |
| Phase 4 — Diff / Architecture Audit | 审查完整 diff：遗漏需求、God Composable、shadow truth、UI-owned canonical state、provider-specific hacks、dead compatibility code、magic constants、duplicated persistence、stale strings/actions。 |
| Phase 5 — Minimal Validation | 按资源预算执行最小有效验证；环境不足或未执行的项目标 UNVERIFIED。 |
| Phase 6 — Packaging | 完成前述阶段审查并如实记录 Gate 状态后，生成补丁及报告；未满足退出标准的 Gate 不得标 PASS，未完成项必须明列。 |

高风险 schema/migration 变更必须有旧库 fixture、恢复测试和独立审查。未验证项目标注 UNVERIFIED，不得因为 AI 推理或旧 CI 通过就写 PASS。

## 5. Acceptance Gate

“实现了一部分”不能自动等价于“Task 完成”。有明确覆盖目标的任务须定义最低完成门槛，并将证据对应到具体功能和 Gate。

例如目标是第一批多 Provider Finance Evidence，只有单个 Provider 实现时不能宣称完成。遇到无法达到门槛的 blocker，应停止相关依赖工作，报告 blocker 并等待 Owner / Reviewer 决策；可独立完成的已授权工作继续推进。

## 6. 资源预算与验证纪律

默认不下载 JDK、SDK 或大型依赖，优先精确修改、代码检查、架构推理和静态验证，不默认执行 Gradle 构建、完整测试套件或无必要重复测试。

已存在工具链时，允许本次授权范围内的针对性单测和必要最小构建。完整测试或额外大型下载仍须先征求 Owner 同意；超出预算前说明目的、范围、命令、预计耗时和成本。

未执行的验证必须标为 UNVERIFIED。代码审查、CI、APK、设备验证分别记录，不相互冒充。

## 7. 架构与代码质量

以根因修复为原则，保护 Canonical owner、数据生命周期、单一 Truth、显式迁移与跨领域边界。

严禁 God Composable、万能 Manager、重复状态、死参数、布尔状态机、UI 直接操作 DAO、无意义兼容层和便利性影子持久化。发现重大替代方案时先报告并征求 Owner 意见。

## 8. Patch 与独立 Review 流程

默认交付 `git format-patch` 及报告；不得擅自执行第 1 节禁止的远端或发布动作。

流程：Owner 给出 Task → Sol 本地补丁 → 独立 Review → Owner 决定应用/推送 → CI → APK → 真机验收。

Reviewer 必须先检查完整补丁，再统一给出结论与问题清单，不零碎追加阻塞项。审查覆盖 commit、architecture、UI state、Finance write path、migration/import semantics、privacy、maintainability；按需求正确性、架构正确性、代码质量、运行验证四层给出结论。

只有明确 Review PASS 后，Owner 再决定应用与推送；禁止返回补丁后未经 Review 直接安装或合并。CI 通过不是架构通过的替代品。

## 9. 会话恢复与文档 checkpoint

项目不得依赖单一聊天窗口作为唯一事实来源；长期事实须进入仓库文档。永久工作流、Review Gate、模型策略、工程红线、阶段与验证纪律维护在本文件。

新会话恢复时按顺序读取：

1. [文档库 README](../README.md)。
2. [文档索引](../文档索引.md)。
3. 本开发协作约定。
4. [当前开发状态](当前开发状态.md)。
5. [V16 Owner 决策](2026-10-V16-Owner-决策与实施交接.md)。
6. [G0 契约](../04-统一架构/架构决策记录/V16-G0领域契约与实施交接方案.md)。
7. 相关已确认 PRD，V16 Finance 包括 [已确认增量](../03-产品需求/已确认/财务-V16-已确认增量.md)。
8. 相关架构（V16 包括 [最终架构备忘录](<../04-统一架构/架构决策记录/Life OS V16 最终架构审查与工程交接备忘录.md>)）、必要开发阶段讨论；涉及 V16 再读 [研究包 README](../02-调研/专题调研/2026-10-V15R2至V16-研究/README.md)和相关证据。
9. 核实真实 GitHub branch / HEAD；后续施工还须核对对应 CI 和本地变更。

研究材料不凌驾于 Owner 后续决定；聊天历史中的旧 SHA、branch 和 Task 指令不得优先于最新有效决定、当前状态记录与真实 GitHub 状态。

每个重要阶段结束后更新当前状态：Repository、canonical base、feature branch、exact HEAD、latest CI、current patch、Review result、completed、explicitly unimplemented、unresolved architecture decisions、next task、required external materials。

以下情况应主动更新文档：阶段完成、进入新模块、Canonical schema/owner 变化、真机反馈形成稳定交互规则、已确认决策与旧 PRD 明显不一致、连续重要 Task 导致状态过期、Review 结论变化、canonical base/feature branch 变化、CI 形成稳定基线、重要架构决定、新增待确认事项或即将进入新阶段。

较长开发或 Review 对话中持续维护 checkpoint，准备突然换窗；会话结束前复核，使新会话可仅依靠 repository + docs 恢复工作。
