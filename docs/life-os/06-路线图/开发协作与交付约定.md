# Life OS 开发协作与交付约定

日期：2026-10-15

## 模型使用与任务分配策略

Life OS 开发不默认把所有任务交给最高推理成本模型。

模型选择应按任务性质决定，而不是简单地“越强越好”。

### 主力开发

复杂多文件实现、Review Fix、UI/业务功能施工、跨文件重构：

- 优先使用 GPT-6.1 Sol
- 推荐 High reasoning
- 适合作为主要工程执行模型

### 专家会诊

以下情况再考虑 GPT-6 Astra：

- 核心架构存在多个难以取舍的方案；
- Finance Canonical 数据模型设计；
- Evidence / Reconciliation / Running Balance 等高复杂度语义；
- Room migration 方案存在高风险；
- 非常复杂的 Compose 手势仲裁；
- 主力模型连续两次不能正确解决的局部问题。

Astra 应优先用于“范围较小但深度很高”的问题，
而不是普通大规模施工。

### 不允许用更高 reasoning 替代工程验证

高 reasoning 不能替代：

- requirement checklist；
- diff audit；
- 最小编译验证；
- static grep；
- 独立 code review；
- CI；
- 真机验收。

如果模型没有执行验证，不能因为模型能力强就把结果视为已验证。


## 大任务执行阶段

大型 Codex Task 应优先采用阶段门禁，而不是一次自由执行到底。

推荐阶段：

### Phase 0 — Context / Requirements

仅阅读，不修改代码。

输出：

- 当前真实代码基线；
- Owner requirements matrix；
- 已实现 / 未实现；
- 预计修改位置；
- 架构风险；
- schema 风险；
- 验收标准；
- blockers。

### Phase 1 — Implementation Plan

明确：

- commit 边界；
- owner / repository 边界；
- 数据流；
- state flow；
- 不允许修改的区域。

### Phase 2 — Implementation

按确认后的计划施工。

### Phase 3 — Requirement Audit

实现后重新逐条阅读 Owner requirements。

输出：

| Requirement | Implemented | Evidence |
|---|---|---|

不得仅凭“总体完成”跳过具体需求检查。

### Phase 4 — Diff / Architecture Audit

检查：

- 遗漏需求；
- God Composable；
- shadow truth；
- UI-owned canonical state；
- provider-specific hacks；
- dead compatibility code；
- magic constants；
- duplicated persistence；
- stale strings/actions。

### Phase 5 — Minimal Validation

在不下载新工具链的前提下进行最小有效验证。

若环境不足，必须明确标记 UNVERIFIED。

### Phase 6 — Packaging

只有前述 Gate 完成后，才允许生成 patch / report。


## Acceptance Gate

“实现了一部分”不能自动等价于“Task 完成”。

对于有明确覆盖目标的任务，需要定义最低完成门槛。

例如多 Provider Finance Evidence：

- 如果任务目标是第一批多 Provider 支持；
- 最终只有单个 Provider 实现；

则不得宣称任务完成。

应：

STOP
→ 报告 blocker
→ 等 Owner / Reviewer 决策。


## 独立 Review 流程

Life OS 默认工作流：

Owner
→ 给 Codex Task

Codex
→ 返回 patch / report

Independent Reviewer
→ 审查：
  - commit；
  - architecture；
  - UI state；
  - Finance write path；
  - migration/import semantics；
  - privacy；
  - maintainability。

只有明确 Review PASS 后：

Owner
→ apply / push

然后：

GitHub CI
→ APK
→ 真机验收

禁止：

Codex 返回 patch
→ 未 Review
→ 直接安装 / 合并。


## 会话换窗与上下文恢复协议

由于 ChatGPT / Codex 会话存在上下文长度和会话切换，
Life OS 开发不得依赖单一聊天窗口作为项目唯一事实来源。

长期事实必须进入项目文档。

### 永久规则

进入：

`06-路线图/开发协作与交付约定.md`

包括：

- 工作流；
- Review Gate；
- 模型策略；
- 工程红线；
- Task 执行阶段；
- 验证纪律。

### 当前现场状态

进入：

`06-路线图/当前开发状态.md`

每个重要开发阶段结束后更新：

- Repository；
- canonical base；
- feature branch；
- exact HEAD；
- latest CI；
- current patch；
- Review result；
- completed；
- explicitly unimplemented；
- unresolved architecture decisions；
- next task；
- required external materials。

### 新会话恢复顺序

新的 ChatGPT / Codex 会话开始时，应首先读取：

1. `docs/life-os/README.md`
2. `docs/life-os/文档索引.md`
3. `docs/life-os/06-路线图/开发协作与交付约定.md`
4. `docs/life-os/06-路线图/当前开发状态.md`
5. 当前任务涉及的 Confirmed PRD
6. 当前任务涉及的 Architecture
7. 必要的开发阶段讨论记录

然后检查真实 GitHub branch / HEAD。

聊天历史中的旧 SHA、旧 branch 和旧 Task 指令不得优先于：
当前开发状态 + 真实 GitHub 状态。


## 会话结束前检查

在较长开发 / Review 对话中，应持续为可能的突然换窗做准备。

当出现以下任一情况时，应主动建议更新 `当前开发状态.md`：

- 完成一轮大型 Task；
- Review 结论发生变化；
- canonical base 改变；
- feature branch 改变；
- CI 得到新的稳定基线；
- 决定重要架构事项；
- 新增明确待确认事项；
- 即将进入新的开发阶段。

目标：

即使聊天窗口立即结束，
新的会话也应能仅依靠 repository + docs 恢复工作。

## 1. 文档先行

每次有意义的代码修改，先读 `life-os-docs/docs/life-os/` 中相关 PRD、统一架构、讨论记录和最新开发状态。

权威顺序遵循文档库 README。

尤其必须阅读相关讨论上下文，理解 Owner 的使用方式、被拒绝方案和设计缘由。

发生实质冲突时报告 Owner，不由代码 AI 擅自裁决。

## 2. 外部研究

每次有意义的开发任务都应进行与问题规模相称的外部研究。

优先 Android/官方平台文档、成熟开源实现、上游问题记录、真实产品实践。

说明实际参考来源、采用与拒绝理由。

网络不可用时必须如实报告，不得虚构调研。

## 3. 资源预算

默认不下载 JDK、SDK 或大型依赖。

默认不执行 Gradle 构建、完整测试套件或重复测试。

优先代码检查、架构推理、精确修改和静态验证。

如需超出默认预算的验证，先向 Owner 说明目的、范围、命令、预计耗时和成本，获得批准后执行。

未执行的验证必须标为 UNVERIFIED。

## 4. 架构与代码质量

以根因修复为原则。

保护 Canonical owner、数据生命周期、单一 Truth、显式迁移与跨领域边界。

严禁 God Composable、万能 Manager、重复状态、死参数、布尔状态机、UI 直接操作 DAO、无意义兼容层和便利性影子持久化。

发现重大替代方案时先报告并征求 Owner 意见。

## 5. Patch 与 Review

Codex 默认只返回 `git format-patch`。

不得擅自 push、merge、rebase 远端、force-push 或创建 PR。

Review 必须先检查完整补丁，再统一给出结论与问题清单，不零碎追加阻塞项。

Review 分四层：

需求正确性、架构正确性、代码质量、运行验证。

CI 通过不是架构通过的替代品。

Owner 在补丁通过 Review 后再应用、推送和真机测试。

## 6. 文档 checkpoint

以下情况需要主动更新文档：

- 阶段完成；
- 进入新模块；
- Canonical schema 或 owner 变化；
- 真机反馈形成稳定交互规则；
- 已确认决策与旧 PRD 明显不一致；
- 连续多个重要 Task 导致状态文档过期。

讨论历史保留在 `01-讨论记录`。

调研放在 `02-调研`。

正式产品决定回写 `03-产品需求`。

跨领域架构决定回写 `04-统一架构`。

稳定视觉交互规范放在 `05-界面与体验`。

开发状态和工作流程放在 `06-路线图`。

新增文件时同步维护 `文档索引.md`；有待决冲突时同步维护 `待核对清单.md`。
