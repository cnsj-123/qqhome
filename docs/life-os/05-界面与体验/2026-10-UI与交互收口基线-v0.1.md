## 1. 视觉方向

Home A 是当前首选视觉基准。

Life OS 应呈现编辑式生活手账、纸张、照片、文字、留白与轻量色彩的气质，而不是标准 Dashboard 或大圆角模块卡片集合。

不要求所有页面长得一样。

- Home：生活手账
- Finance：紧凑账簿
- Appearance：主题编辑器
- Closet / Items：收藏册
- Plans / Shopping：工作台
- Calendar / Map / Search：事实投影面

共享 typography、颜色、纸张、图标、动作与间距规则，但各领域拥有适合内容的信息组织方式。

## 2. Typography

必须区分品牌字与日期 Hero。

统一角色至少包括 Wordmark、DateHero、PageTitle、SectionTitle、Body、Meta、Money。

Owner 提供本地字体后，应检查中文字符覆盖、字重、许可证、数字形态与 fallback，再纳入现有 LifeFonts。

Figma 精确字号和字重尚未通过连接器核实，不应凭截图推断为已确认数值。

## 3. Home

首页以日期、照片堆、Memory、Ahead 为核心。

普通内容通过留白与文字层级组织，减少横线与无意义边框。

Home 不是模块入口 Dashboard。

顶部保留品牌、快速记录、日历、地图等轻量动作；位置按最新 Figma 与真机反馈校准。

空状态自然留白，不导入虚构照片、天气、生活事件。

## 4. Finance

### V16 Finance 三主空间

V16 一级空间固定为“账簿 / 账户 / 分析”，不再以“总览 / 流水 / 账户 / 分析”四个平级 Tab 组织。

账簿首页融合纳入账户净额、月度收支摘要、可折叠月/周历、连续日期流水与固定记一笔入口。整体为紧凑账簿，不堆叠大型状态卡。

账户以资产/负债、常用/归档分组，优先使用完整可读的紧凑行，支持较长账户名称及多币种。

分析默认个人消费，可明确切换真实现金进出；日期、账户、分类、事项筛选独立于其他 Finance 空间，图表可钻取对应明细。

待确认、往来、对账属于任务工作入口，不作为永久一级 Tab。

手势遵守区域所有权；系统 Back 优先，Finance Pager、Calendar、Drawer、Companion 不能互相抢占。厂商原子岛不是 App 内复核和跨 App 小票的硬依赖。

产品权威见 [Finance V16 已确认增量](../03-产品需求/已确认/财务-V16-已确认增量.md)。

### 记一笔

必须是单连续编辑上下文。

支出/收入/转账、金额、分类、账户、时间、备注、标签、业务性质在一个页面内完成。高频选择原地展开，低频内容按需折叠，不叠加多层选择浮窗。

### 分类

优先两级视觉选择，底层可支持更深层级。

采用图标、最近使用、搜索、紧凑网格或标签选择。

分类表示消费内容；报销、代付、代拍、分账属于资金业务性质。

用户自选分类图标为明确产品需求，须使用稳定 iconKey 并由 Finance Category owner 持久化；若当前数据库不支持，安排显式迁移，不使用 UI 假状态。

### 账户

适应十几个至数十个账户。

采用紧凑分组、折叠、搜索与短行展示；不使用大量超高账户卡片。

不同币种不得硬加为一个金额。

### 流水余额

目标为金额下方显示该笔交易后的对应账户余额。

此值必须由可靠账务顺序与余额锚点推导，不能使用当前余额冒充，也不能持久化为第二份余额 Truth。

若当前数据条件不足，明确标记未实现，不能显示假数。

### 历史报销

旧账中“已报销”是有意义的历史业务状态。

导入应批量识别并保留该事实，但不能在到账账户未知时伪造现金收入。

## 5. Appearance

Appearance 是编辑器，而不是一组即时写入的设置开关。

主题色、功能页风格及效果调整先进入草稿，实时预览；最终统一由“保存主题”提交。

颜色编辑弹窗内部的保存只更新主题草稿。

可见控制名保留“色彩氛围”。

不透明度 0–100 语义真实；背景柔化受边界约束；预览与运行使用共同效果模型。

功能页四种风格保持各自辨识度。

## 6. 手势与性能

手势必须跟手、连续，并遵守系统返回边缘优先级。

Finance 月历、周历、Pager、Shell 负一屏、Function Page、Companion 的手势所有权应清晰，不允许重复拦截。

先诊断首帧闪屏、卡顿和突兀转场根因，不额外添加开屏动画掩盖问题。

支持减少动画与低性能设备合理降级。

## 7. 工程待实现与验证

V16 上述产品选择已确认；分类图标元数据、稳定账务排序、running balance、旧账业务关系 resolution/provenance、外部支付身份与 Evidence 模型仍需工程实现、迁移与恢复验证。具体表结构等工程细节另行审查，不重新表决已决产品方向。

本文件不能被解读为这些能力已经实现。

本规范随真机 Review 更新；涉及 Canonical 数据结构的决定须回写 Finance PRD 或架构决策，而不是只留在 UI 文档中。
