# Life OS V16 决策收敛研究：从 V15 R2 真机问题到一次性 V16 实施边界

## 研究结论与已经可以定下来的方向

这轮研究后的结论，比此前《V15-R2 到 V16 架构与产品决策报告》更收敛：**你这次选的方向整体是成立的，而且可以组合成一套一致的 V16，不需要再给三套完整 Architecture 让你选。** 后续只需要对少数仍存在真实工程取舍的点逐个决定。你选择的 40 个功能也不是 40 个彼此独立的 Feature；它们实际上可以归并成六条能力链，因此可以作为**同一个 V16 release scope**，但不能作为一个巨型 commit 或一个 Codex 一口气写完的任务。候选清单和此前研究中的依赖关系基本支持这种收敛。fileciteturn0file1 fileciteturn0file3

当前 GitHub 上用于 V16 继续研究的真实 Android 基线是 `feature/life-os-v15-ui-convergence-p1-r2-final`，HEAD 为 `245e1475cd1d47a4205ab49f75d5e06d22de701c`；这个提交就是此前收敛 CI 测试的提交。fileciteturn2file0L1-L2 对应 Android CI Run #50 已经 `success`，所以 V16 不应重新解决已经绿掉的编译/测试问题。fileciteturn3file0L1-L2 另一方面，你之后的 V15 R2 真机报告依然发现冷启动白屏、Finance 手势冲突、自动发现没有响应、通知监听连接状态异常、导入卡顿和大量 Finance UX 摩擦，这再次证明了 **CI green ≠ device acceptance green**。fileciteturn0file4 旧 R2 交付报告自身也曾明确把真机验证标记为未验证，因此这轮不应该用旧的静态“PASS”覆盖真实设备反馈。fileciteturn0file6

我建议把你这轮选择正式理解成下面的 V16 决策：

| 决策面 | V16 收敛结论 |
|---|---|
| Gesture | **B：区域 / 能力契约**。不再每页自己抢 Pointer，也不做一个 Root 万能手势引擎 |
| Finance IA | **B 的三主空间骨架 + A 的总览能力融入账簿首屏** |
| Running Balance | **A：实时 Projection → 真机/Benchmark profile → 只有证据表明确有必要才上 B checkpoint cache** |
| Multi-account Identity | **B：小型 External Identity / Signal / Account Binding 模型** |
| Evidence / Proposal | **B：持久化最小 Evidence Summary + Extraction Version + 关联关系 + Proposal** |
| Accessibility | **B 自动稳定采样 + C 主动读取兜底** |
| 半屏小票 | **B 跨 App receipt overlay 为主；C 只留 presentation adapter 接口，不把 V16 成败绑在厂商“原子岛”上** |
| 功能范围 | 你选择的 **40 项全部进入 V16 产品范围**，但按依赖分内部 Gate |
| 发布方式 | **一次 schema migration、一个 V16 产品版本、一次最终集中真机验收**；开发过程分阶段提交和验证 |

这里最值得定死的是 Finance IA：**我不建议再保留“总览 / 流水 / 账户 / 分析”四个平级大页面。** 你现在给出的具体想法其实已经自然解决了 A/B 冲突：

> **账簿 = 总览 + 流水的融合页；账户、分析保持独立。**

也就是一级结构变成：

```text
账簿
账户
分析
```

而：

```text
待确认
往来
对账
```

是“有事情时才出现”的工作入口，不再占三个永久一级 Tab。

这也和成熟记账产品常见的“账户/交易 register 本身就是核心工作空间”一致。Realbyte Money Manager 的 Home 可以在 Calendar、Weekly、Monthly、Summary 间查看同一批财务内容，日期点击后直接看到当天交易，而不是把日期与交易拆成完全不同的工作域；Actual 和 GnuCash 的对账能力也都是从账户/交易 register 延伸出来，而不是另造一个平行账本。citeturn5search30turn5search34turn5search0turn11search1

因此，我认为这轮已经**不需要再讨论三套完整 V16 Architecture**。剩下应当逐项决定的是诸如 OCR 模型 bundled/unbundled、是否真的需要 running-balance checkpoint、跨 App 文本输入采用系统 IME 还是局部 fallback 等较小技术选择，而不是重新选一次大架构。

## 交互架构与 Finance 首屏应该怎样落地

### Gesture B 应该变成“手势所有权表”，而不是更多 if/else

当前 `LifeGestures.kt` 已经有两个正确的种子：一是把 Android 系统返回边缘排除出去；二是通过轴向意图判断后再消费 Pointer。但现在仍然主要是若干 `pointerInput` owner 各自协商：普通横滑阈值约 56dp，而 Companion 上滑只从底部约 40dp 区域开始。fileciteturn9file0L1-L2 这正好解释了你的真机感觉：**不是单个阈值绝对错，而是不同区域没有一份统一的所有权契约。** 你在真机报告第一页就已经描述了 Finance 内页横滑、功能页右滑和 Companion 上滑之间的不一致。fileciteturn0file4

Android Compose 官方的 nested scrolling 模型本身就是通过 pre-scroll、child consumption、post-scroll 来协调父子滚动；官方 Pointer 文档也强调事件会沿初始命中的链条传播，消费状态会影响其他节点，所以这种场景更适合“区域先确定 owner，再由 nested scroll/高级手势组件处理”，而不是 Root 层最后凭一个 `dx/dy` 猜所有页面的意图。citeturn8view3turn0search1turn0search2 Android 的 predictive back 也要求不要让 App 的全局横滑长期劫持系统 Back 路径，因此目前“系统返回边缘永远优先”应当继续保留。citeturn8view4

V16 可以把它收敛成这份契约：

| 起手区域 | 横向手势 | 纵向手势 | Shell 是否可抢 |
|---|---|---|---|
| Android 系统返回边缘 | 系统 Back | 正常内容 | **永不抢** |
| Finance 账簿普通内容 | 左滑 → 账户；右滑在第一页边界才可去功能页 | Ledger 滚动 | Pager/内容优先 |
| Finance 账户 | 左右 → Finance 内部前/后页 | 账户列表滚动 | 不直接开功能页 |
| Finance 分析 | 右滑 → 账户；左边界无下一页 | 分析内容滚动 | 不直接开功能页 |
| Finance 底部导航表面 | **右滑可直接开功能页** | 上滑 → Companion | 这是显式 Shell 手势区 |
| 月历本体 | 左右换月/周 | 上下折叠、再交给流水 | **月历优先** |
| 流水列表 | 不主动拥有 Shell 横滑，除 Finance pager 明确接管外 | 列表滚动 | 内容优先 |
| Home 底部 Companion 区 | 不与系统 Back 边缘冲突 | 上滑 → Companion | Companion owner |
| Drawer / Sheet / Viewer | 当前浮层自己处理 | 当前浮层自己处理 | 下层不参与 |

这里的关键不是再规定一个神奇的 56dp，而是：

> **同一根手指在一次 Gesture 生命周期里只能有一个 owner，owner 一旦过 touch slop 确认，不允许中途从 Calendar 转成 Shell、从 Ledger 转成 Companion。**

月历折叠则应该有离散锚点，例如：

```text
Month
  ↕
Week
  ↕
Collapsed / Ledger
```

释放后一定 settle 到某个锚点，而不是停在你真机报告里那种“半月历悬在中间”的状态。Compose 的 nested scroll 正好适合由父容器吸收折叠距离、子列表继续消费剩余滚动。citeturn8view3

### Finance 应该是“三空间”，但账簿首屏要保留你要的“大局观”

你说“总额最好第一眼能看见”，我赞成，但必须先定义这个“总额”是什么，不能再把几个不同的 Finance 概念揉成一个数字。

当前代码已经明确区分真实账户 Flow 与最终个人消费；账户余额也是 `openingBalance + anchor 之后的真实 entry` 的 Projection，而不是统计数字。fileciteturn4file0L1-L2 fileciteturn6file0L1-L2 所以 V16 首屏顶部建议明确分成两个语义层：

```text
账簿                                      搜索

账户净额
¥ 37,109.50

本月个人
支出 ¥ 4,812        收入 ¥ 12,000

待确认 3 · 往来 2       ← 只有 >0 才出现

           月历 / 周历
──────────────────────
今天
  午餐                     -38.50
  工资                  +12,000
...
```

**第一眼的大数字应该叫“账户净额”或“当前账户净额”，而不是模糊的“本月余额”。** 若以后有人民币、美元、积分等多币种账户，没有获批汇率来源时就分别显示，不允许静默相加。当前 Projection 本身已经按 `currencyCode` 分统计维度，这个基础应该继续利用。fileciteturn6file0L1-L2

月度横向摘要则应使用你真正关心的：

```text
个人消费 / 个人收入
```

而不是“所有账户 OUT / IN”。否则信用卡还款、银行卡转微信零钱、退款到账都会把这个摘要污染。当前 Event 模型已经有 PERSONAL、SPLIT、PROXY_PURCHASE、REIMBURSABLE 等 Nature，也有 REFUND、REIMBURSEMENT、SETTLEMENT、REBATE 等 Flow Role，可以继续成为 Personal Projection 的依据。fileciteturn5file0L1-L2

因此你的 A+B 最合理的最终表达是：

**A 的“首屏一眼知道我现在怎样”留着；B 的“减少一级页面和状态卡”也留着。**

账户页则按你说的做：**资产 / 负债 → 常用 / 归档 → 紧凑单行**。现在 `FinanceAccountKind` 已有 BANK_CARD、CREDIT、INVESTMENT 等类型，但没有完全明确的 `ASSET/LIABILITY` 账户分类，因此我建议 V16 的账户 profile 明确加入可编辑的账户资产属性，而不要永远从 `kind` 猜。fileciteturn4file0L1-L2 长名称、信用卡、多个同名银行账户、多币种都会让全页双列卡片很快失效；双列只适合账簿首屏放少数账户摘要。

分析页则必须拥有自己的 `AnalysisQueryState`：

```text
dateWindow
accountIds
categoryIds
tags
eventNature / flowRole
viewBasis = PERSONAL | CASH_FLOW
project / context
```

账簿也有自己的 `LedgerQueryState`。F12“点统计进入构成流水”不是把一个全局 filter 改掉，而是**把当前分析条件复制成一个明确的 `FinanceQuerySpec`，然后以 drill-down route 打开流水**。退出后原账簿状态原样保留。这也正好为 F10、F11 和 F62 打统一基础。

## 逐笔余额、对账与多账户身份是 V16 的“可信度层”

### Running Balance 的 A → profile → 必要时 B 是正确选择

当前代码有一个非常正确的原则：

> `FinanceProjection` 是 read-only projection，**不独立持久化 balance**。fileciteturn6file0L1-L2

应该保留。

V16 的逐笔余额应该这样生成：

```text
Account Anchor
      │
      ▼
该账户全部有效真实流水
      │
按有效账务时间排序
      │
      ▼
running balance projection
      │
      ├── 当前余额
      ├── 每笔之后余额
      └── 对账比较值
```

而不是：

```text
finance_entry.balanceAfter = ...
```

后一种方案一旦补录上个月交易，就必须修改之后几乎所有 transaction row；这会制造大量可过期 Truth。Beancount 的 balance assertion 设计也把已知余额看成“检查账本正确性的 checkpoint”，而不是把每条 transaction 的运行余额永久写进 transaction 本身。citeturn6search0

当前 `balanceAnchorAt` 还有一个非常重要的语义：锚点以前后补的历史记录不会反过来改变“当前已知余额”。fileciteturn4file0L1-L2 这个设计应该继续存在，但 V16 要把它升级成用户可理解的 F19：

```text
余额起点
2026-10-18 10:00
建设银行
¥ 8,351.29
```

再叠加 F24 的多个 **Balance Observation**：

```text
9月30日  银行账单余额   ¥ 7,502.11
10月15日 App余额      ¥ 8,120.20
10月18日 手动核对     ¥ 8,351.29
```

这些 Observation 的作用是：

> “我在这个时点知道真实机构给出的余额是多少。”

它们是**验证点**，不是自动调账。

Actual 的 reconciliation 也是拿账本与银行账本比较，并区分 cleared / uncleared；GnuCash 的 reconciliation 则明确要求 statement date、starting balance、ending balance、reconciled balance 和 difference，最终目标是把差异核到零。citeturn5search0turn11search1turn11search3

因此 F17/F18/F19/F20/F24 应该作为一整套做：

| 能力 | V16 语义 |
|---|---|
| F17 逐笔余额 | 从完整账户 Ledger Projection 得到，不从当前筛选列表重新算 |
| F19 余额起点 | 用户确认的基准余额与时点 |
| F24 多余额观测 | 外部事实检查点，不直接改账 |
| F18 对账工作台 | 账户 + 时点 + 外部余额 + 未核记录 + Difference |
| F20 可信度 | 说明“这个余额为什么值得信”，而不是一个 AI confidence 百分比 |

推荐的可信度不是 67%、93% 这种假精确度，而是人能看懂的状态：

```text
✓ 已核对至 10月15日
≈ 从已核对余额推算
! 与最新余额相差 ¥32.50
? 锚点前历史可能不完整
```

F22 信用卡也必须挂在这套体系上，而不是另造信用卡账本。信用卡消费产生个人消费；还信用卡则是银行账户 → 信用账户的 **Transfer**，不能再计算一次消费。Actual 的 transfer 也是两个账户里的 linked halves，金额联动，而账户各自的 cleared/reconciled 状态仍可独立；这正适合信用卡付款与到账日期不完全一致的现实情况。citeturn11search0 当前 Life OS 已经有双腿 `FinanceTransferEntity`，所以这里应扩展，而不是重做资金流模型。fileciteturn4file0L1-L2

这里我会再加一个 V16 必需但此前尚未正式实现的字段：

```text
occurredAt   = 真实消费/操作发生时间
postedAt?    = 银行/信用账户真正入账或记账时间
recordedAt   = Life OS 收到/记录它的时间
```

对现金或没有 posted 信息的记录，`ledgerAt = occurredAt`；有机构 statement posted time 时，对账和账户 Running Balance 应优先使用 `postedAt`。这也是此前 R2 报告里已经明确延期到 Finance v5 的领域之一。fileciteturn0file6

**A → profile → B** 的实现上，我建议 A 不是“每个 Composable 每次重组都重新 fold 全库”，而是：

```text
Room snapshot change
      ↓
Repository / Projection 层
      ↓
每账户排序一次 + 顺序扫描一次
      ↓
BalanceRowProjection
      ↓
UI 只消费结果
```

然后用 Macrobenchmark 真机测 1k / 10k / 50k 等 synthetic ledger。Android 官方建议用 Macrobenchmark 的 `FrameTimingMetric` 测交互 jank，并用 StartupTimingMetric 测 TTID/TTFD；Baseline Profile 也应该覆盖真实关键路径，而不是先凭感觉优化。citeturn4search1turn4search7turn4search8 **只有 A 在真实数据规模上造成可测量的卡顿，才引入 B 的 versioned checkpoint cache。**

而 checkpoint 仍然只能是：

```text
DERIVED CACHE
```

不能进导出 Truth、不能成为交易余额来源，任何 backdate/edit/void 都必须从影响点开始失效。

### Multi-account Identity B 也应该保持“小”

当前 Evidence 已经明确写了：

> `transactionSource` 和 `paymentChannelHint` 是 hint，不能成为 Finance Account identity。fileciteturn7file0L1-L2

这条必须继续保留。

V16 不需要一开始建立一个庞大的金融机构身份图谱。建议只做三层：

```text
External Identity Signal
        │
        ▼
External Instrument
        │
        ▼
Account Binding
        │
        ▼
Life OS Finance Account
```

比如：

```text
支付宝页面
  provider = ALIPAY

页面支付方式
  CREDIT_CARD
  建设银行

用户确认
  “这是我的 建行信用卡”

之后：
  signal → external instrument → Finance Account
```

Binding 必须由**用户明确确认**建立。以后识别到相同 instrument 时，可以推荐账户；匹配不唯一就继续让用户选。即使用户日后修改 Binding，也绝不能追溯改写已经确认过的历史 entries。

银行卡弱标识如果未来必须用于区分多个同类卡，不建议把完整卡号或纯 4 位 suffix hash 存进数据库；纯四位值的搜索空间太小。更合理的是用户主动允许后，对最小 normalized identifier 做设备本地 HMAC，密钥放 Android Keystore。Android Keystore 的密钥材料可以保持不可导出，并原生支持 HMAC-SHA256。citeturn9search0 但这仍然只应作为 matcher，不是显示给用户的“账户事实”。

## Evidence、Accessibility 与半屏小票应该合并为一条可靠管道

你选择 **Evidence B + Accessibility B/C + Receipt B/C** 后，V16 最关键的一条架构应该变成：

```text
Notification
Accessibility auto
Accessibility manual
User OCR image
Import / other future source
        │
        ▼
  Evidence Summary
        │
        ├── Extraction version
        ├── strong reference digest
        ├── source/provider/channel
        ├── amount/time/role candidates
        └── NO raw page dump
        │
        ▼
Correlation / Evidence links
        │
        ▼
     Proposal
  可编辑、可稍后
        │
        ▼
 Review Surface
  App / Overlay / future vendor surface
        │
        ▼
Explicit Confirm
        │
        ▼
Canonical Finance Truth
```

这比当前 v4 真正缺的就是中间那层“Evidence 可以活下来”。当前 `NormalizedTransactionEvidence` 已经有 provider、reference digest、extractionVersion、transactionSource、paymentChannelHint、relatedOrderDigest，但代码明确说明 **Room v4 没有正式 provenance/correlation columns**，因此很多 hint 到 Proposal 后不会持久保留。fileciteturn7file0L1-L2 你的 F43“同笔交易多来源合并”和 Multi-account Identity 在这个限制下做不漂亮，所以 V16 这一步值得正式迁移。

Evidence 仍然必须保持最小化。建议持久化：

```text
source family
host provider
observedAt
extractionVersion
strongReferenceDigest?
amount / currency candidate
occurredAt candidate
direction / role candidate
transactionSource hint
paymentChannel hint
privacy-safe instrument signal?
```

不持久化：

```text
Accessibility tree
整个页面文本
完整通知原文
地址
电话
姓名
完整银行卡号
聊天上下文
物流/行程全文
```

F43 的合并策略也不要变成“金额 + 时间相近 = 同一笔”。Actual 的导入系统优先使用来源提供的稳定 imported identifier；没有稳定 ID 时才使用金额、日期、payee 等相似条件辅助匹配，并且仍让用户核查结果。citeturn5search3turn5search19 Life OS 应采用同样的强弱关系：

```text
strong source reference
    → 可以高度确定关联

same order digest / explicit relation
    → 可以确定或高置信关联

amount + near time + source
    → duplicate candidate only

amount + near time across apps
    → NEVER auto merge
```

### Accessibility 的 B+C 应该修的是“可观察的采集状态机”

你真机遇到的最大问题并不是某个支付宝字段少写了一条规则，而是：

> **打开了真实详情页，Life OS 完全没反应。** fileciteturn0file4

因此 V16 如果只是再加十几个 parser string，风险仍然很高。

Android Accessibility 自身就提供了适合稳定采样的能力：Service 可以限制关心的 package；`notificationTimeout` 可以延迟过于频繁的事件、等待事件生成趋稳，从而减少昂贵 IPC；服务也可以只监听需要的事件类型。citeturn6search5turn6search6

推荐自动 B 做成：

```text
SUPPORTED HOST FOREGROUND
        ↓
relevant accessibility event
        ↓
stability / debounce window
        ↓
bounded snapshot
        ↓
adapter parse
        ↓
RECOGNIZED
LOW_CONFIDENCE
NOT_DETAIL
UNSUPPORTED_VARIANT
        ↓
Evidence / no Evidence
```

一次失败可以在**同一个 bounded capture session** 内做少量稳定重采样，而不是看到 `TYPE_WINDOW_CONTENT_CHANGED` 就无限扫整棵树。

而 C“主动读取当前详情”应该是同一个 Acquisition Coordinator 的显式命令，不是另写一套 parser。最可靠的实现分两档：

```text
有 Overlay 能力
→ 在支持的宿主页面显示很轻的“读取当前详情”
→ 用户点时目标 App 仍在前台
→ Accessibility 立刻读取

无 Overlay 权限
→ “读取下一次详情”
→ Life OS armed session
→ 用户回到目标 App
→ 下一个稳定详情页只读一次
```

这比强求 Quick Settings 打开后立刻读取当前 root 更可靠，因为系统 Shade 本身会改变 foreground window。

还必须增加一层**隐私安全的诊断状态**。它不是完整的 F41 新功能，而是 B+C 能否真机验收的必要基础：

```text
Accessibility permission     已开启
Service                      connected
当前宿主                     Alipay
最近事件                     14:32:05
最近读取                     LOW_CONFIDENCE
原因                         缺少订单号
Proposal                     未产生
```

不记录页面原文，只记录 reason code、provider、app version、时间和计数。这样下一次“没有反应”就能知道到底是：

```text
Service 根本没事件
节点树未稳定
页面 fingerprint 不支持
缺字段
重复被去重
Proposal 已经产生
```

通知监听同样如此。Android 官方明确规定，`NotificationListenerService` 应等待 `onListenerConnected()` 后再执行操作；`onListenerDisconnected()` 后不会继续收到事件，而 `requestRebind()` 是这时允许调用的恢复入口。citeturn6search3 所以你真机报告里的“授权还在，但 Life OS 显示未连接”必须在 V16 变成一个真正的连接状态机，而不是把 permission granted 当成 connected。fileciteturn0file4

### B 半屏小票值得继续，但当前实现还不是可编辑版本

有趣的是，V15 R2 已经存在一个真正的跨 App 半屏实现：`FinanceReceiptOverlay` 使用 `TYPE_APPLICATION_OVERLAY`，高度约半屏，并显示金额、来源、时间、账户、分类、说明、性质以及确认/稍后。fileciteturn8file0L1-L2

问题在于它当前明确带：

```text
FLAG_NOT_FOCUSABLE
```

Android 官方定义就是：这种 Window 不会得到 key input focus，也不需要和 IME 交互。citeturn6search4 所以现在它可以“确认”，但不适合你想要的：

> 在小票里直接改金额 / 分类 / 账户 / 备注并保存。

V16 B 的最佳实现不是把它直接变成一个巨大表单，而是两态：

```text
Receipt Preview
非 focusable
轻量、安全
     ↓ 点修改
Receipt Edit Mode
明确拿焦点
```

主要编辑动作甚至可以尽量不依赖 IME：

```text
金额 → F01 自定义数字/计算器键盘
账户 → 最近账户 / picker
分类 → 图标 + 最近分类
性质 → chips
备注 → F02 可选；真正需要文字时才请求 IME
```

这样普通自动小票通常两三下就能确认，而不会把第三方 App 完全遮住。

`SYSTEM_ALERT_WINDOW`/`TYPE_APPLICATION_OVERLAY` 仍然应当是**可选增强权限**。Android 对 Application Overlay 明确要求该特殊权限，而且系统可以调整其大小、位置或可见性；Android 12 以后 Overlay 对下层触摸透传也有额外安全限制。citeturn6search4turn8view2 所以没有 Overlay 权限时，必须完整退化到：

```text
通知
→ Life OS 内 Receipt Bottom Sheet
```

不能让自动发现失去确认入口。

至于 C 的“原子岛接口”，我同意你现在的态度：**留接口，能实现更好，不能也完全不影响 V16。**

Android 现在的 Live Updates 是为“正在进行、用户发起、时间敏感”的活动设计的，官方甚至明确说已经结束的过去事件不要使用 Live Update；因此“支付已经完成，现在请确认这张小票”并不是它的自然用途。citeturn8view0 Notification Bubble 的主要语义又长期是 conversation，而且 Android 11+ 的 Bubble notification 还和 conversation requirements 紧密相关。citeturn8view1

因此正确抽象是：

```text
ReceiptSurface
    ├── InAppReceiptSurface
    ├── ApplicationOverlaySurface   ← V16 主力
    └── VendorReceiptSurface        ← 接口
```

以后某个 OEM 真有适合的官方 API，再接最后一个；Proposal/Confirm 业务逻辑一行都不需要重写。

## 你选的四十项功能不是四十个 Feature，而是六个系统能力

把你这次选的 40 项逐项做依赖分析后，我认为**没有哪一项需要因为架构冲突直接删掉**。真正需要调整的是实现顺序与“功能归属”。

| 能力链 | 你选中的功能 | 应该形成的产品能力 |
|---|---|---|
| 快速记账与账簿 | F01、F02、F03、F05、F07、F09、F10、F11、F12、F13、F16 | 一套快速 Editor + Ledger/Calendar + Typed Query |
| 账户可信度与对账 | F17、F18、F19、F20、F22、F24、F25 | Running Balance + Observation + Reconciliation + Import |
| 批量、附件与往来 | F14、F32、F33、F34、F35、F36、F37、F38、F40 | Event / Obligation / Adjustment 工作空间 |
| 自动发现与复核 | F43、F44、F45、F46、F47、F48 | Evidence Graph + Proposal Queue + Receipt |
| 消费理解 | F51、F54、F55、F56 | 固定/弹性 + 温和异常 + Context |
| 数据与长期使用 | F60、F61、F62 | Portability + Memory + Read-only Natural Query |

**快速记账这一组应该共享一个 `FinanceEditSession`。** F01 的金额键盘、F02 备注可空、F03 快选、F05 连续补账和 F07 草稿恢复都不应该分别发明状态。普通记账时“唯一必须输入的文本”甚至可以为零：金额由数字键盘输入，账户/分类是选择，备注完全可空。你真机报告里“时间靠手输、分类难点、金额键盘不顺、备注像必填”本质上就是 Edit Session 没有以“最快写下一笔”为中心。fileciteturn0file4

F09/F16 应共享一套 calendar navigation state：

```text
Year grid
   ↓
Month
   ↓
Week
   ↓
Day
   ↓
Ledger group
```

“最近访问月份”只是 Navigation history，不是 Finance Truth。

F10/F11/F12/F62 则应该统一成一个 `FinanceQuerySpec`。F62 自然语言**绝不能直接操作 DAO 或生成 SQL 后裸执行**，而应该：

```text
“去年去上海吃饭花了多少”
        ↓
NaturalQuery parser
        ↓
FinanceQuerySpec
日期：2025
项目/地点：上海
分类：餐饮
basis：个人消费
        ↓
显示解析 chips
        ↓
执行已有 Query Engine
```

也就是说 F62 是 F10 的另一种输入法，而不是另一套搜索引擎。对于说明、标签等自由文本，未来可以把 AppSearch 当成可重建的 local search index；Android 的 AppSearch 是设备端结构化/全文搜索能力，适合做 derived index，但不应成为第二套 Ledger Truth。citeturn8view6

### F33–F40 应成为“往来工作页”，而不是往 Transaction 堆更多布尔字段

当前 Event 模型其实已经很接近正确基础：Event 有 `personalShareMinor`，一个 Event 可以连接多个 Entry，每个 link 有 allocated amount 与 Flow Role；ExpectedFlow 还可以表达“以后预计会来/会走的钱”。fileciteturn5file0L1-L2

所以：

```text
F34 部分报销 / 分次到账
F37 部分退款
F38 返利部分到账
```

都不需要复制原交易。

例如一笔 ¥100 公司餐：

```text
Event: 公司餐 ¥100
  PAYMENT       -100  招行
  expected reimbursement +100

第一次报销
  REIMBURSEMENT +60

第二次
  REIMBURSEMENT +40
```

Event 的个人最终成本最终可以是 0，但账户的真实钱仍然一进一出。

F35“别人替我付 / 我欠别人”和 F36“多人不等额分摊”则需要在现有 Event 外补一个很小的 `Party / Obligation` 层，因为目前 `personalShareMinor` 能告诉系统“我的份额多少”，却不能完整回答“谁替谁垫了多少、我欠谁”。fileciteturn5file0L1-L2 Splitwise 的核心模型也正是把“谁支付”和“每个人应承担多少”分开，并支持 exact amount、percentage、shares 等分法。citeturn5search45turn5search46 Expensify 的 split 机制同样要求拆分后的金额守恒。citeturn5search55

V16 不用成为 Splitwise，但最小模型应能表示：

```text
Event
  total economic cost

PartyShare
  我       ¥40
  A       ¥60

Obligation
  debtor=A
  creditor=我
  amount=¥60

实际到账
  SETTLEMENT / REIMBURSEMENT links
```

F40“一件商品成本时间线”就只是这些事实的 Projection：

```text
购买       ¥399
平台退款   -¥50
返利       -¥20
运费        +¥8
──────────────
最终成本    ¥337
```

不要建立第二张 `item_cost_ledger`。

### F51/F55 不应该把 Life OS 变成重预算软件

你的 F51“固定负担 / 弹性消费”+ F55“轻量弹性预算”非常适合做一个比传统 category budget 更轻的结构。Monarch 的 Flex Budgeting 也是把固定、非月度和 flexible spending 分开，其中 flexible spending 可以作为一个高层 bucket，而不是每个咖啡/午饭分类都必须分配预算。citeturn5search50turn5search53

Life OS 可以更轻：

```text
固定
房租 / 订阅 / 必须还款

弹性
餐饮 / 娱乐 / 随手购物

本月弹性额度  ¥3,000
已经使用      ¥1,840
还可使用      ¥1,160
```

不需要 V16 同时建立完整 Envelope Budgeting。

F54“温和异常”也应该只是 Projection：

```text
“这笔餐饮比你最近通常记录的高一些”
“这笔可能和昨天一笔重复”
“这个账户最新核对余额有 ¥18.20 差额”
```

只有提示，不自动修改分类、不自动作废、不创造 Truth。

F56 项目/旅行/兴趣专题成本建议采用**Finance Event → Life Context typed link**，而不是复制交易。例如“日本旅行”模块引用一批 Finance Event；账目仍只有一份。

F61“消费生活回忆”则建立在这些 Context 和已确认 transaction 上，而且**默认关闭**。它只能从 Canonical Truth 和用户允许的附件生成摘要，不能把 Accessibility 原文、地址、行程、支付页面私密字段翻出来做“惊喜回忆”。

### F45/F48/F60 也有明确边界

F45“规则建议 + 试运行”非常值得做，但规则建议只能：

```text
发现模式
→ 建议规则
→ dry-run
→ 给你看将影响哪些候选/交易
→ 你确认
```

不能建议完直接批量改账。Lunch Money 的 Rules 已经采用类似思路：相似交易的修改可以形成规则，而对历史相似交易应用时会让用户先审查具体目标；CSV/PDF 导入也先 mapping、dedupe、Review，再 Import。citeturn5search4turn5search1

F48 OCR 最安全的入口就是 Android Photo Picker，而不是请求整个相册权限。Android 官方 Photo Picker 允许用户只授权选中的媒体，也支持持久 URI grant。citeturn4search5turn10view3 OCR 可以直接进入同一个 Evidence pipeline：

```text
用户选图
→ OCR
→ Evidence candidate
→ Proposal
→ Review
```

原图 OCR 完即释放；只有用户同时选择 F32“作为凭据保存”时才长期关联。

ML Kit 当前中文 Text Recognition 有两种分发：Play Services unbundled 每 script 约增加 260KB，但首次可能要下载模型；bundled 约增加 4MB，但安装后立即可用。citeturn10view0turn10view1 **对 Life OS 我更倾向 V16 先使用 bundled Chinese OCR**，因为 F48 本来就是自动发现失败时的可靠人工兜底，第一次使用却告诉用户“模型还没下载好”会破坏这个定位；最终是否接受约 4MB 增量，可以在 APK size Gate 再决定。

F60 则要分成两个出口：

```text
人看的
CSV / PDF / 可读账单

机器可恢复的
versioned complete export
accounts
entries
transfers
events
relations
tags
bindings
evidence summaries（可选）
attachments（可选）
...
```

“完整导出”必须保存 stable IDs 和关系；单一扁平 CSV 无法完整表示 Event ↔ Entry ↔ Obligation ↔ Evidence 这种图关系。

## V16 需要一次集中数据迁移，但不应该到处新增 Truth

根据当前 Room v4 和你已经选中的功能，**V16 需要 schema migration 基本已经不可避免**。这不是为了“架构漂亮”，而是当前代码已经明确缺少 persistent Evidence provenance / Account Binding；而你又选择了 F18 对账、F24 Observation、F43 多 Evidence 合并、F07 草稿、F11 保存视图、F32 附件、F35/F36 往来关系。当前 R2 报告也明确把 Evidence graph、Account Binding、running balance/reconciliation 等标为当时未实现的后续项。fileciteturn0file5 fileciteturn0file6

按当前 v4 基线，如果中间没有别的 schema bump，V16 可以集中成 **Room v5**。我建议 schema 只增加真正需要持久化的事实：

| 层 | V16 应持久化 | 不应持久化 |
|---|---|---|
| Entry | `postedAt?` 等真实账务信息 | `balanceAfter` |
| Account | asset/liability profile、信用卡周期配置 | 页面展开状态 |
| Running balance | Anchor 已有；Balance Observation、Reconciliation | 每笔运行余额 |
| Quick entry | Draft | 数字键盘按键状态 |
| Query | Saved View 的 QuerySpec | 当前滚动位置的 SQL 副本 |
| Identity | External identity/instrument signal + Account Binding | Provider→Account 隐式映射 |
| Evidence | 最小 Evidence Summary、ExtractionVersion、关系 | 原始 Accessibility tree / 完整通知 |
| Attachment | 用户显式选中的 attachment ref / managed copy metadata | 自动截第三方页面 |
| Relations | Party / Obligation / Share | 第二套“往来账本” |
| Budget | fixed/flexible classification、轻量 budget settings | 每月重复统计缓存 |
| Context | Finance Event ↔ Life module relation | 项目里再复制一份金额 |

而以下都应该是 Derived Projection：

```text
账户当前余额
逐笔余额
本月个人支出/收入
退款后商品成本
报销剩余待收
返利剩余待收
我欠某人 / 某人欠我当前净额
预算进度
异常提示
项目成本
消费回忆候选
分析图表
```

B 方案的 balance checkpoint 如果最终 profile 证明需要，则应明确叫：

```text
cache
```

并带 projection/version key，可随时删除后重建，**不进入完整数据导出，不作为 Restore 必需数据**。

OCR 也遵循这个分层。Android Photo Picker 可以只给用户选中的媒体权限；对文档类附件可以使用 Storage Access Framework 的 `ACTION_OPEN_DOCUMENT` 并取得持久 URI 权限，而不是申请整个共享存储。citeturn4search15turn4search28

Evidence 中需要保存某个弱支付工具 matcher 时，也不要把隐私字符串塞进 `description` 或一个 JSON shadow store。Account Binding 是正式 typed data；Evidence 是正式 typed data；Canonical Entry/Event 仍然只有一套。

这也是我认为 V16 最重要的数据库原则：

> **Schema 可以变大，但 Truth 不能变多。**

## 一次性 V16 应该怎样开发，而不是再陷入“修一个红点打一片补丁”

你希望“下一阶段实施路线与验收目标 V16 一次性先做了”，我认为可以，而且这正是现在更好的做法。

但“一次性”应该定义成：

> **一次确定 V16 完整 Scope + 一次 Room migration + 一套完整 CI/Benchmark + 最后一个整合 APK 做一次集中真机验收。**

而不是：

> 一个 Agent 一次生成 50,000 行代码、一个 mega commit、然后第一次编译才发现 30 个架构问题。

推荐的 V16 release train 如下。所有阶段都属于 **同一个 V16**，不需要你每阶段装一个 APK 验收。

| 内部 Gate | 先做什么 | 为什么 |
|---|---|---|
| Foundation | v4→V16 schema migration、Truth invariants、QuerySpec、Gesture ownership contract、Performance baseline | 后面 40 项依赖它 |
| Ledger UX | 新三空间 IA、F01/02/03/05/07/09/10/11/12/13/14/16 | 先让每天最常用的记账和查账真正舒服 |
| Trust | F17/18/19/20/22/24/25 | 建立余额与对账可信度 |
| Relations | F32/33/34/35/36/37/38/40 | 用 Event/Obligation 一次解决报销、代付、退款、返利 |
| Acquisition | Identity B、Evidence B、Accessibility B+C、F43–F48、Receipt B | 自动发现不再靠碰运气 |
| Insight & Portability | F51/54/55/56/60/61/62 | 全部建立在前面稳定 Truth 与 Query 上 |
| Convergence | 全 CI、migration test、Macrobenchmark、七宿主、整包真机验收 | 最后才交 Owner V16 APK |

其中 **Foundation 必须先记录 R2 的性能基线再重构**。Android 官方提供 StartupTimingMetric 的 TTID/TTFD 和 Macrobenchmark 的 FrameTimingMetric；Compose 官方也明确建议先测量再定位重组/布局/绘制开销，而不是凭经验到处 `remember` 或 `derivedStateOf`。citeturn7search1turn4search0turn4search11

你真机报告里的冷启动“几秒白屏”也应该正式变成性能 Gate。Android 的 SplashScreen 应在 App 第一帧准备好时自然退出；如果用 `setKeepOnScreenCondition`，该条件会在每帧绘制前执行，必须很快。citeturn7search2 Android 官方性能指南给出的理想目标是 cold start 约 500ms 或更低，同时 Play Vitals 把 5 秒以上 cold start 视作 excessive；Life OS 不必为了一个理论数字作弊，但至少应该把 R2 真实基线、TTID 和 TTFD 测出来，并显著消灭你看到的白屏阶段。citeturn7search7turn7search8

我建议 V16 最终 Review 不再只问“代码有没有”，而直接采用这套验收：

| 验收领域 | V16 Release Gate |
|---|---|
| 启动 | 冷启动无独立白屏阶段；系统 Splash → coherent Home；记录 TTID/TTFD，并相对 R2 基线无回退 |
| 手势 | 前述 ownership matrix 全通过；系统 Back 不被抢；Calendar 必定 snap；Finance 内页不误开功能页 |
| Finance IA | 第一屏无需滚动即可看到账户净额和本月摘要；主一级只有账簿/账户/分析 |
| Filter state | Ledger、Accounts、Analysis 状态互不暗改；图表 drill-down 用显式 QuerySpec |
| 快速记账 | 备注可空；金额自定义键盘；最近账户/分类；连续补账；杀进程后草稿恢复 |
| Running balance | Backdate、Edit、Void、Restore 后所有后续行余额正确重算 |
| 对账 | Observation 与计算余额差异可解释；Difference=0 才完成 reconcile；已核区间被历史修改时明确失效或警告 |
| 信用卡 | 消费只统计一次；还款为 Transfer；账单周期与还款可核对 |
| 往来 | 部分报销、多次到账、别人替付、不等额分摊、部分退款、返利都不制造重复消费/收入 |
| Import | 有真实阶段进度；Preview 可取消；批量修正先给 diff；Commit 原子；Undo 有边界 |
| Identity | Host/Source/Channel 永不直接等于 Account；只有明确 Binding 可以建议 canonical account |
| Evidence | 多来源可汇聚；冲突不覆盖；ExtractorVersion 不参与 transaction identity |
| Accessibility | 七个宿主逐个真机；自动 B + 主动 C；无法识别必须给 reason code，而不是“没反应” |
| Notification listener | 区分 permission / connected；disconnect 后有正确 rebind/恢复状态 |
| Receipt | 无 Overlay 权限仍有 notification+App 复核；有权限可跨 App 修改常用字段再显式确认 |
| OCR | 只处理用户选择的图片；图片默认不保留；OCR 结果永远先进入 Proposal |
| Privacy | DB/log/export 默认无 raw Accessibility tree、页面全文、地址/电话等；附件必须显式添加 |
| Export | 人类可读导出 + versioned complete export；关系与 stable IDs 可验证 |
| F62 | 自然语言只生成可见 QuerySpec；任何不确定解析先显示条件，不进行写操作 |
| 性能 | Macrobenchmark 覆盖启动、Drawer→Finance、账簿滚动、月历折叠/换月、连续记账、Import Preview；FrameTiming 与 R2 baseline 对比 |
| 数据迁移 | 真实 v4 backup → V16 migration；账户、entry、transfer、event、allocation、proposal/import 语义全部保持 |
