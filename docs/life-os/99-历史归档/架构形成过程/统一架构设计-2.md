继续。现在进入 **Architecture Synthesis 第五轮：Invariant & Failure Review**。

这一轮我不再帮架构“找优点”，而是故意从最坏情况攻击它：AI 越权、两个 Domain 抢同一事实、同步只来了一半、媒体上传和数据库事务不同步、旧设备不认识新数据、恢复后云端又把错误同步回来……

结果是：**整体架构扛得住，但有几个必须补成正式不变量，否则实现阶段很容易被“方便一下”破坏。**

---

# 1. 第一刀：AI 绕过 Proposal，直接调用 Domain Command 怎么办？

我们现在规定 AI：

```text
Model
  ↓
Tool
  ↓
Action Gate
  ↓
Proposal
```

但假设开发时有人觉得：

> “这个 `recordWear()` 很安全，让 AI 直接调用算了。”

那 Proposal 边界立刻被绕过。

因此之前的：

> “AI 写入都要确认”

不能只是一条产品规则。

必须成为**权限模型本身**：

```text
AI principal

可以：
truth.read
proposal.create

不可以：
truth.commit
```

真正的 Commit capability 只属于：

```text
USER_DIRECT
USER_CONFIRMED_PROPOSAL
SYSTEM_RECOVERY
TRUSTED_SYNC_REPLICATION
```

所以未来不是：

> AI Tool 自己记得先创建 Proposal。

而是：

> **AI 从 Capability 层根本拿不到 Commit API。**

这个不变量非常重要。

---

# 2. 第二刀：两个 Domain 都认为自己拥有同一个 Event

例如油画课。

Hobbies 认为：

> 我拥有 `ClassSession`。

Membership 开发者又觉得：

> 次数扣减需要 `MembershipClassEvent`。

Calendar 又创建：

> `CalendarClassEvent`。

马上出现三份。

所以我们上一轮提出的 **Fact Ownership Registry** 必须从“文档规范”升级成架构资产。

例如：

```text
Canonical Type Registry

hobbies.class_session
Owner = Hobbies Domain

finance.transaction
Owner = Finance Domain

commerce.purchase
Owner = Commerce Domain

health.medication_intake
Owner = Health Domain
```

其他 Domain 只能：

```text
reference
query
propose
react
```

不能：

```text
redefine
```

如果一个新模块需要一种现有事实：

优先关联已有 canonical type。

只有确实不存在新的语义对象时才能申请新 type。

这以后非常适合做 Architecture Review checklist。

---

# 3. 第三刀：ChangeSet 成功了，但 Derived 更新失败

例如用户确认一次油画课。

Canonical commit 成功：

```text
ClassSession created
Membership delta -1
```

随后：

```text
Daily Summary update
Search index
Home summary
```

跑到一半 App 崩了。

如果我们要求：

> Canonical + 所有 Derived 必须一个巨大事务同时成功

系统会越来越脆。

正确原则应该是：

# **Truth commit is authoritative; Derived consistency is eventual and repairable.**

也就是：

```text
Domain Transaction
      ↓
Truth committed
      ↓
Derived invalidation queued
```

之后 Derived Worker 慢慢追。

如果失败：

System Health 可以知道：

> Search index 比 Truth revision 落后。

然后补建。

因此每类 Derived 最好能记录类似：

```text
derived_revision
source_revision
```

如果：

`derived_revision < source_revision`

就知道它过期了。

这也是为什么 Derived 永远不能反过来成为 Canonical 查询的唯一依据。

---

# 4. Search Index 命中了已经被删除的对象怎么办？

这也是同一个问题。

Truth：

```text
Item deleted_at = ...
```

FTS 还没更新。

Search 结果仍然搜到它。

所以 Search 结果不能：

> index 命中 → 直接当真。

应该：

```text
Search Index
   ↓ candidate IDs
Canonical read
   ↓
filter current state / permission / tombstone
   ↓
Result
```

因此：

> **Derived indexes return candidates, Canonical layer decides validity.**

Embedding Search、AI resurfacing、推荐候选也一样。

这条很重要。

---

# 5. 第四刀：数据库 Commit 成功，但 Sync Queue 没写进去

如果：

```text
Truth transaction commits
```

然后下一行代码：

```text
enqueueSync()
```

App 正好在中间被杀。

那么这次修改永远不会同步。

所以：

> **Canonical change 和 replication intent 必须拥有同一原子边界。**

最自然的方式是类似 Transactional Outbox：

```text
DB transaction:

1. mutate Truth
2. write ChangeSet
3. write Sync Outbox record

COMMIT
```

之后 Sync Worker 读取 Outbox。

这样即使 App 下一秒死亡：

变化仍然等着同步。

这可能是这一轮最重要的工程补强之一。

---

# 6. 同样，Attention 也不能靠 Commit 后“顺手发一下”

例如：

会员真正到期。

Truth 更新后应该产生：

```text
Attention Candidate
```

但如果创建 Attention Candidate 失败，不应该回滚会员事实。

所以它和 Derived 类似：

Canonical transaction 记录一个：

> domain event / outbox signal

之后 Attention Processor 再消费。

所以未来可以出现统一：

# **Post-Commit Event Stream / Outbox**

用于：

```text
Derived invalidation
Sync
Attention evaluation
Background automation
```

而不是每个 Domain Commit 后直接调用五个模块。

这能极大减少耦合。

---

# 7. 第五刀：事件被消费两遍怎么办？

比如：

```text
ClassSessionCreated
```

Membership consumer 本应扣一次。

但 Worker 崩溃重启，消息又消费一次。

如果结果：

> 再扣一次课时

就很危险。

所以所有跨 Domain side effect 必须支持：

# **Idempotency**

例如：

Membership delta 带：

```text
source_event_id = class_session_123
effect_key = membership.consume
```

数据库保证：

同一个：

`source_event_id + effect_key`

只能应用一次。

于是 consumer 运行 1 次还是 5 次：

结果相同。

这个原则还适用于：

Import
Sync
Backup jobs
Notification
Media processing

---

# 8. 第六刀：一个跨 Domain Command 执行到一半

例如用户确认一件衣服订单。

我们需要：

```text
Transaction
Purchase
Item
Relations
```

如果四个都是同一 `lifeos.db`：

很好，可以一个 DB transaction 原子 Commit。

但未来某些 side effect 在外部：

比如：

上传媒体
调用第三方
创建远程 Calendar

就不可能和 SQLite 一个事务。

所以要明确：

## Canonical transaction

必须本地原子。

## External side effect

必须：

```text
after canonical commit
+
retryable
+
idempotent
+
status tracked
```

不能：

> 外部 API 成功一半，然后本地回滚，系统却装作什么都没发生。

如果外部 action 本身很重要：

它应该有自己的：

```text
Pending
Succeeded
FailedRecoverable
CompensationNeeded
```

状态。

---

# 9. 第七刀：媒体 Binary 已上传，但 MediaAsset Commit 失败

这和上面非常像。

例如：

照片上传云端成功。

但随后本地：

`MediaAsset` 创建失败。

现在云端有一个“孤儿文件”。

反过来：

MediaAsset commit 成功，但上传失败。

现在数据库认为有媒体，但云端没有。

所以媒体必须采用：

# **Manifest + Object lifecycle**

例如：

```text
MediaAsset
    state = LOCAL_ONLY
            BACKUP_PENDING
            BACKED_UP
            SOURCE_MISSING
```

Cloud Object 也有自己的 object ID。

孤儿对象由：

> Garbage Collector

在确认没有 canonical MediaAsset 引用后清理。

不能依赖：

> “每次操作都会刚好全部成功。”

---

# 10. 第八刀：Sync 只收到 ChangeSet 一半

假设一个 ChangeSet 同时：

```text
Create Item
Create Purchase
Link Item → Purchase
```

远端只先收到前两条。

UI 此刻看到一个没有来源的 Item。

如果同步以“字段变化流”裸奔，就容易出现。

因此多对象逻辑操作需要：

> **Atomic Sync Bundle**

或者至少：

```text
change_set_id
part_count
part_index
```

远端必须知道：

> 这个 logical operation 还没完整到达。

对于必须原子可见的 ChangeSet：

全部到齐后再 apply。

对于可部分独立的 ChangeSet：

才能增量 apply。

这个区别需要 Domain Command 声明。

---

# 11. 第九刀：同一个 ChangeSet 被 Sync 重放十次

网络协议里重复投递是正常现象。

因此 Remote Apply 必须：

```text
change_set_id
```

作为 Idempotency Key。

设备保存：

> 已应用 ChangeSet。

同一 ChangeSet 再来：

忽略。

所以我们的同步目标应该是：

> **at-least-once transport + idempotent application**

而不是幻想：

> 网络层一定 exactly once。

后者很难，也没必要。

---

# 12. 第十刀：旧客户端完全不认识一个新 Event Type

例如新版新增：

```text
event_type = PET_VET_VISIT
```

旧平板不懂。

它不能：

> schema validation failed → 删除。

也不能：

> 转成 GenericEvent 再保存，把专业内容丢掉。

正确状态是：

```text
Opaque Canonical Object
```

旧设备知道：

* ID；
* revision；
* object kind；
* extension envelope；
* sync metadata；

但不理解业务 payload。

UI 可以：

> “此记录由较新版本 Life OS 创建，请更新 App 查看详情。”

但是同步和备份仍然：

> 原样保留。

所以我们上一轮的：

**Unknown ≠ Delete**

现在应该升级成：

# **Unknown Canonical Preservation Invariant**

---

# 13. 第十一刀：旧客户端修改了同一个对象怎么办？

例如新版 Item 多了：

```text
sustainability_note
```

旧平板不知道。

它只改：

> display name。

如果旧平板执行：

```text
PUT whole object
```

就会把未知字段全部覆盖掉。

因此 Command 必须尽可能：

# **Patch semantics**

而不是：

> Replace entire canonical object。

例如：

```text
UpdateItemName(
  id,
  expected_revision,
  new_name
)
```

而不是：

```text
saveItem(oldClientSerializedObject)
```

这会自然保留客户端不了解的字段。

这是版本错位设备安全的关键。

---

# 14. 第十二刀：Proposal 已经过期，但用户几个月以后点“确认”

例如 AI 在 6 月发现：

> 商品价格 ¥599。

9 月才打开 Candidate 点确认。

实际价格、关联 Transaction、甚至 Product identity 都变了。

所以 Proposal 不能被当作：

> 永远有效的待执行 Command。

每个 Proposal 在 Commit 前都应该：

```text
Revalidate
```

检查：

* target revision；
* evidence 还在吗；
* 冲突吗；
* 外部来源是否变化；
* Domain invariant 是否仍成立。

必要时：

> “这条候选已经和当前数据不一致，我重新整理了一下。”

而不是机械提交三个月前的状态。

所以：

> **Proposal is a plan, not a reserved truth.**

---

# 15. Snoozed Proposal 也不能永远堆着

这暴露 Proposal Layer 的生命周期问题。

Proposal 至少应该支持：

```text
ACTIVE
SNOOZED
STALE
SUPERSEDED
CONFIRMED
REJECTED
EXPIRED
```

其中：

**SUPERSEDED**

尤其重要。

比如系统第一次提出：

> 这可能是一笔 Food。

后来有了更完整账单：

产生更准确 Proposal。

旧的就不要还显示。

而是：

> superseded_by = proposal_2

这能防止 Inbox 污染。

---

# 16. 第十三刀：Entity Merge 错了，拆开时怎么办？

比如：

`小王`

和

`王老师`

误合并。

半年后发现不是一个人。

如果 Merge 是：

> 把所有 relation 的 `person_b` ID 直接替换成 `person_a`，然后删除 B。

基本无法恢复。

所以 Merge 必须通过 Recovery Layer 做成：

# **Reversible Identity Resolution**

至少保留：

```text
pre_merge_identity
source_identity mappings
affected relations
change_set
```

Split 时能恢复。

甚至更稳的模型是：

> canonical identity resolution layer

把多个 source identities 映射到一个 canonical Person，而不是物理摧毁原始 source identity。

这和 Import provenance 非常契合。

---

# 17. 第十四刀：用户恢复昨天 Snapshot，但云端有今天的错误数据

这是非常危险的恢复循环。

假设：

今天误删 500 条。

同步上云。

用户：

> 恢复到昨天。

本机恢复成功。

然后 Sync 一连：

> “云端 revision 更高”

又把那 500 条删回来。

所以 Disaster Restore 不能只是：

> 替换本地 DB。

它必须创建：

# **Restore Epoch / Recovery Generation**

例如：

```text
sync_epoch = 42
```

恢复以后：

```text
sync_epoch = 43
```

告诉 Sync：

> 这是一次有意的全局恢复，不是一个落后的旧设备。

然后需要策略：

> 重新发布恢复后的 canonical state / recovery ChangeSet。

这样云端才知道：

> 用户主动回到了这个状态。

而不是继续“纠正”回来。

这是这一轮另一个必须正式设计的点。

---

# 18. 同理，Restore 后不能简单复用所有旧 Outbox

否则：

昨天快照里可能还有：

> 当时尚未发送的旧 Sync Event。

恢复以后全部重新发送，可能制造幽灵操作。

因此 Snapshot 必须明确包含：

> Canonical state 的一致恢复点

但 Sync Runtime 状态需要：

> 恢复流程重新初始化/重建。

这再次说明：

> **Backup State ≠ Sync Runtime State。**

---

# 19. 第十五刀：Backup 本身损坏怎么办？

我们不能只检查：

> backup 文件存在。

应该至少拥有：

```text
snapshot manifest
schema version
created_at
database checksum
media manifest hashes
encryption metadata
```

创建 Backup 后可以后台做：

> Verify。

重大恢复点最好标：

```text
VERIFIED
UNVERIFIED
FAILED
```

System Health 显示的是：

> 最近一个**已验证**恢复点。

不是：

> 最近执行过一次 backup job。

这两个完全不同。

---

# 20. 第十六刀：Creative Vault 的引用泄漏出去

我们虽然物理隔离 Vault，但假设普通 Life OS Relation 表出现：

```text
related_to = vault_artifact_193
```

即使普通世界看不到内容，它已经泄漏：

> Vault 有一个对象、什么时候创建、和什么有关。

这违反我们之前：

> Creative Vault 对普通 AI/Global Search 连 metadata / relation edges 都不可见。

所以必须更严格：

# **No cross-boundary canonical reference into Vault**

普通世界不能持有：

> Vault object ID。

如果用户显式从 Vault 导出一个作品：

那应该创建：

> **新的 exported Artifact**

进入普通 Life OS。

它不是：

> 指向私密原件的 live link。

这样 Vault 的存在本身都不泄漏。

---

# 21. 第十七刀：Plugin 的 Extension 被其他 Domain 依赖

例如 Coffee Plugin 创建了：

```text
plugin.coffee_geek.roast_profile
```

后来某个第一方 View 保存一个 Relation：

> depends_on plugin-specific object。

插件卸载后：

这个关系断了。

所以规则应该是：

> **Core/first-party canonical facts不能依赖 plugin-owned semantics 才能保持自身有效。**

Plugin 可以：

> 附加信息。

但不能让核心事实的合法性依赖插件存在。

如果一个插件概念逐渐成为广泛必需：

应该通过正式 Schema Evolution 晋升成 First-party/Core capability。

不是偷偷依赖 Plugin namespace。

---

# 22. 第十八刀：Plugin 更新后不认识自己旧 Payload

这是 Plugin 自己的 migration 问题。

Core 只负责：

> Payload 不丢。

插件自己负责：

```text
schema_version 2 → 3
```

如果 Plugin migration 失败：

Life OS 不能：

> 删除坏数据。

而应该：

> 插件扩展暂不可用，原数据已保留。

这样第三方 bug 不会破坏人生主库。

---

# 23. 第十九刀：Domain Consumer 之间形成循环

比如：

Hobbies ClassSession →

Membership 扣次数。

Membership balance changed →

某个 automation 又创建 Hobbies Event。

无限循环。

所以 post-commit event 需要：

```text
causation_id
correlation_id
origin
```

每个自动 reaction 必须知道：

> 谁导致了我。

Domain policy 还能声明：

> 这个事件不应该再次触发同类自动效果。

否则复杂系统后期非常容易产生 event loop。

---

# 24. 第二十刀：同一个现实动作被两个输入源捕获

例如：

银行导入：

> ¥699。

购物截图：

> ¥699 羽绒服。

Companion 又听你说：

> “刚买了件羽绒服。”

系统可能产生：

三份 Proposal。

不能让用户确认三遍。

因此 Proposal Layer 还需要：

# **Candidate Correlation / Dedup**

把多个 Evidence：

```text
Bank Transaction
Screenshot
Conversation
```

聚合成一个：

```text
Purchase Proposal
```

显示：

> “我从账单、截图和刚才的聊天里判断这是同一次购买。”

Evidence 越多，Proposal 越有信心。

但 Truth 仍然只有一份。

这个其实会成为 Life OS AI 很有优势的地方。

---

# 25. 第二十一刀：用户明确确认，但 Domain invariant 已被别人改变

例如：

Proposal：

> Item 加入 Closet。

在确认前，这个 Item 已经被退货。

用户仍点：

> 确认加入衣橱。

这就是为什么 Commit 必须带：

```text
expected_revision
```

和：

> Revalidation。

可能弹：

> “这件商品现在已标记为退货，仍然要作为拥有物加入吗？”

由用户决定。

不能根据旧 Proposal 机械执行。

---

# 26. 第二十二刀：跨 Domain 删除

用户删除：

> Purchase Event。

但它关联：

Item
Transaction
Warranty
Plog

如果直接 Cascade Delete：

灾难。

所以 Canonical Relation 默认不应该广泛使用：

> destructive database cascade。

删除 Purchase：

首先是：

```text
soft delete / correction
```

然后 Domain Policy 判断：

Item：

是否仍然有其他 acquisition source？

Transaction：

本身仍然存在，不删。

Plog：

引用失效还是保留历史？

也就是说：

> **Database FK cascade ≠ Domain deletion semantics。**

外键可以保证引用完整性。

但业务删除必须由 Domain Command 明确决定。

---

# 27. 第二十三刀：用户删除 Evidence，但 Fact 仍然存在

例如：

用户确认：

> A 的生日是 3 月 18。

来源是一张截图。

之后用户删除截图。

是否应该删 Birthday？

不应该自动删。

因为 Fact 已经被用户接受。

但 provenance 应该更新为：

> original evidence unavailable.

这说明：

```text
Evidence lifecycle
≠
Fact lifecycle
```

除非 Fact 本来就属于：

> 仅引用外部动态来源、从未用户确认。

这个要由 Domain policy 决定。

---

# 28. 第二十四刀：事实被纠正以后，基于旧事实生成的 Narrative 怎么办？

比如 Travel Trip 日期从：

10/1

改成：

10/2。

Plog 里已经有一句：

> “10 月 1 日到了上海。”

如果 Plog 是：

**自动动态 View**

可以更新。

但我们之前已经定：

> 手工作品/排版成品不能随事实变化自动重排。

所以要明确两种引用：

```text
LIVE REFERENCE
```

跟随 Canonical Fact。

和：

```text
SNAPSHOT REFERENCE
```

保存创作时的 presentation snapshot。

Composition 可以提示：

> “引用的源内容已经更新。”

但不能偷偷改作品。

这也是之前 Share/Portfolio 决策的重要技术表达。

---

# 29. 第二十五刀：Home/Memory resurfacing 把用户不想看到的人重新提出来

即使 Fact 还存在，Resurfacing Preference：

> 不主动出现 A

必须在：

```text
Derived candidate
→ Attention/Resurfacing policy
```

最终过滤。

不能因为 Search Index 命中就直接上 Home。

所以：

> **Existence ≠ Visibility ≠ AI Access ≠ Resurfacing**

这条之前已经出现，现在经过 failure review 应该升格成正式隐私不变量。

# 30. 经过这一轮攻击，我觉得我们需要正式定义一组 Architecture Invariants

> **Every asynchronous boundary assumes duplication, interruption and reordering.**

Life OS Architecture Overview

--- Title: Life OS Architecture Overview Version: 0.1 Status: DRAFT Authority: Canonical Architecture Baseline Last Updated: 2026-09-30 Owner: Product Owner Scope: Life OS Related System: Ombre Brain / Context Gateway --- # Life OS Architecture Overview ## 1. Purpose Life OS is a local-first personal life operating system designed to preserve a person's long-term factual life history, relationships, media, plans, possessions, knowledge, creations, and experiences while presenting them through domain-specific professional views. The architecture is based on one central principle: > One personal world, many professional views; AI is a permissioned companion, not the owner of the database. 中文： > 一个真实的个人世界，多种专业视图；AI 是有权限边界的伙伴，而不是数据库的主人。 Life OS is intended to remain usable and trustworthy over many years. Its architecture therefore prioritizes identity continuity, recoverability, local ownership, cross-domain consistency, controlled AI access, evolvability, and data portability over short-term implementation convenience. --- # 2. Architectural Position Life OS is not a collection of independent mini-app databases. Finance, Shopping, Closet, Garden, Health, Travel, Hobbies, Knowledge and other modules are domain-specific views over a shared canonical personal world. A real-world fact should have one canonical identity even when it appears in multiple modules. For example, a painting class may simultaneously appear in Hobbies, Calendar, Membership, Life Marks and Home, but it remains one canonical `ClassSession`. Similarly: ```text ClassSession │ ├── displayed by Calendar ├── consumes Membership ├── counted by Life Marks ├── shown in Hobbies └── may appear on Home

The architecture therefore separates factual ownership from presentation ownership.

A module may display or reference another domain's fact without creating a duplicate copy of that fact.

3. System Definition

Life OS is the canonical personal world model.

It answers questions such as:

What actually happened?

Who or what was involved?

When and where did it happen?

What evidence supports this information?

Which object is the same object across different modules?

Ombre Brain is a separate memory and context system.

It answers a different class of questions:

What should the AI remember right now?

Which past memories are relevant to this conversation?

What long-term relational context should be surfaced?

The two systems cooperate but must not collapse into one another.

Life OS Canonical personal facts │ │ authorized fact context ▼ Context Gateway ▲ │ relevant memory context Ombre Brain AI memory / recall / relationship context │ ▼ Model

Life OS records the world.

Ombre Brain determines what may be useful to remember about that world at a particular moment.

The modules do not own isolated copies of the person's life.

They query and compose professional views from shared canonical facts.

6. Canonical World Model

Life OS currently defines seven conceptual world primitives.

They are conceptual architectural primitives rather than a commitment to seven physical database tables.

PrimitivePurposeEntityA relatively persistent person, place, object or concept with stable identity.EventSomething that actually happened.IntentSomething planned, intended or desired but not yet established as having happened.RelationA meaningful ongoing or structural relationship between canonical objects.EvidenceThe source from which information was obtained.ArtifactA durable piece of content or creation.CompositionA presentation project that arranges existing content without duplicating its canonical originals.

Examples of Entity include Person, Place, Product, Item, Plant, Book and Membership Account.

Examples of Event include Purchase, Payment, Meal, Wear, Wash, Class Session, Concert, Medical Visit and Medication Intake.

Examples of Intent include Planned Event, Goal, Project, Task and Recurring Plan.

Examples of Artifact include photographs, knowledge documents, paintings and Plog narratives.

Examples of Composition include Travel Books, Garden Yearbooks, Plog layouts and portfolios.

7. Identity Model

Canonical identity is independent from display names and external systems.

person_018XYZ...

is the person's identity.

The strings:

小王 王明 王老师 Wang Ming

are display names or aliases.

Likewise, external identifiers such as Google Contact IDs, Calendar UIDs, bank transaction identifiers and Android media URIs do not become Life OS canonical IDs.

They are external identities or provenance.

This makes renaming, reconnection, provider changes and future migration possible without breaking internal relationships.

The architecture follows:

Names may change. Identity must not.

8. Event-Centric Life History

Many real-world relationships are not naturally binary.

For example:

2026-09-30 Oil painting class Instructor: Wang Place: Studio Membership consumed: 1 Media: 3 photos

This is better represented as one Event surrounded by participants and related objects than as several unrelated pairwise relationships.

Wang ↑ instructor │ Me ─ participant → ClassSession ← location ─ Studio │ consumes ↓ Membership

Events may also be composite.

A Trip may contain a Flight, Hotel Stay, Meal, Concert and Shopping Event while each child remains independently identifiable.

Trip ├── Flight ├── Hotel Stay ├── Meal └── Concert

part_of does not duplicate the child event.

9. Intent Is Not Event

Plans and actual life history must never be silently conflated.

Intent "I will attend a concert next month" ≠ Event "I attended the concert"

A planned event may later be associated with an observed event, but a lack of actual event evidence must not be interpreted as completion.

The same distinction applies to medication plans, travel plans, goals, tasks and recurring schedules.

Similarly:

No record does not mean the event did not occur.

The architecture therefore distinguishes unknown state from explicit observed absence.

10. Truth Layer

The Truth Layer is not a claim of metaphysical certainty.

It represents the current canonical version of information that has been accepted into Life OS.

A fact may later be corrected.

For example:

2026-09-30 → Restaurant A

may later be corrected to:

2026-09-30 → Restaurant B

The current canonical value changes, but the history of the correction remains available through the Recovery Layer.

Therefore:

Confirmed does not mean immutable.

Truth means:

Current accepted canonical state.

11. Proposal Layer

Uncertain or externally inferred changes do not directly modify canonical truth.

They enter the Proposal Layer.

Typical proposal producers include AI, OCR interpretation, importers, entity resolution, automatic transaction association, synchronization conflict handling and conversation-derived candidates.

Evidence / Context ↓ Interpretation ↓ Proposal ↓ Review / Revalidation ↓ Domain Command ↓ Canonical Truth

A proposal is a potential change plan, not a reserved future fact.

Before commitment it must be revalidated against current canonical state.

Proposal states may include active, snoozed, stale, superseded, confirmed, rejected and expired.

Multiple evidence sources may be correlated into one proposal.

For example, a bank transaction, shopping screenshot and Companion conversation may collectively support one Purchase proposal rather than three separate candidates.

12. Draft Is Not Proposal

Drafts and proposals are conceptually distinct.

A Draft is user-owned unfinished content.

Examples include an unfinished Plog or partially edited Portfolio.

A Proposal is a proposed change to canonical Life OS data.

Examples include an AI-detected Purchase or a possible Person merge.

Therefore:

Draft ≠ Proposal ≠ Truth

Drafts must not acquire the psychological meaning of uncompleted system obligations.

13. Evidence and Provenance

Evidence is preserved separately from extracted or accepted information.

For example:

Screenshot ↓ Evidence OCR ↓ Extraction "This appears to be a ¥699 jacket" ↓ Proposal User confirms ↓ Purchase / Product / Transaction

The original screenshot remains available.

The OCR output can be replaced by a better OCR model without altering the evidence.

The accepted fact may later remain valid even if the user chooses to delete the original screenshot.

Therefore:

Evidence lifecycle and fact lifecycle are not identical.

Provenance should answer:

Where did this information come from?

Possible sources include direct user input, external imports, screenshots, URLs, financial feeds, files, AI extraction and previously confirmed canonical facts.

14. Derived Data Layer

The Derived Data Layer exists for performance, search and intelligent assistance.

Typical derived data includes full-text search indexes, OCR text, semantic embeddings, AI tags, thumbnails, previews, daily summaries, monthly summaries, timeline caches and resurfacing candidates.

Derived data is not canonical truth.

It may be removed and reconstructed.

Truth / Evidence ↓ Derived Data

not:

Derived Data ↓ Truth

When a search index returns an object ID, the canonical layer must still validate its current state, permissions and deletion status before presenting it as a valid result.

The governing rule is:

Derived results produce candidates; canonical state decides validity.

15. Recovery Layer

Life OS is designed around recoverability rather than constant defensive confirmation.

The Recovery Layer contains concepts such as ChangeSets, Undo, soft deletion, Trash, edit history, correction history, conflict preservation, Import rollback, migration recovery points and backup snapshots.

Every meaningful canonical modification should be associated with a human-comprehensible logical operation.

For example:

"Record oil painting class" may modify: Hobbies session Membership balance Calendar projection Life Marks count

Undo should revert the logical operation, not force the user to manually reverse each consequence in separate modules.

The architecture therefore introduces ChangeSet as a core mutation concept.

16. Command Architecture

Canonical writes do not occur through unrestricted database access.

Every canonical mutation follows a controlled command path.

Command ↓ Capability Check ↓ Central Action Gate ↓ Domain Command Handler ↓ Validation / Revision Check ↓ ChangeSet ↓ Atomic Canonical Commit

A successful command records:

Known Actor Known Authority Allowed Capability Validated Domain Command Expected Revision ChangeSet Atomic Commit

The persistence implementation may evolve, but this semantic boundary must remain.

17. Query Architecture

Reads and writes intentionally have different levels of strictness.

Canonical writes are conservative.

Queries may freely compose professional views.

For example:

ClosetItemDetailQuery(item_id) Item + Product + Purchase + Transaction references + Wear Events + Wash Events + Media + Closet Extension ↓ ClosetItemView

The resulting view is not another canonical object.

It is a projection.

Therefore:

Persistence Entity ≠ Domain Model ≠ View Model.

18. Domain Ownership

Every canonical fact type has one semantic owner.

For example:

finance.transaction Owner = Finance Domain commerce.purchase Owner = Commerce Domain hobbies.class_session Owner = Hobbies Domain health.medication_intake Owner = Health Domain

Other modules may query, display, reference, react to or propose modifications involving these facts.

They must not redefine duplicate canonical representations.

This rule is formalized through the Domain Ownership Registry.

A painting class therefore remains one ClassSession.

Membership consumes a lesson because of it.

Calendar displays it.

Life Marks counts it.

Home may surface it.

No second MembershipClassEvent, CalendarClassEvent or LifeMarksClassEvent is created.

19. Domain Extensions

The canonical model remains small.

Professional modules extend it rather than replacing it.

For example:

Core Item ↓ Closet Extension size fabric measurements fit

or:

Core Event ↓ Concert Extension artist venue performance-specific properties

The preferred pattern is:

World Primitive ↓ Canonical Domain Object ↓ Domain Extension ↓ Cross-domain Relations ↓ View Composition ↓ Module UI

This allows modules to remain professionally rich without fragmenting the canonical world.

20. Reusable Domain Patterns

Several recurring domain structures are treated as patterns rather than new world primitives.

PatternUseComposite EventA large event containing independently identifiable child events.ObservationA timestamped observed value or state, especially useful in Health.Ledger / DeltaBalance derived from incremental events, useful for Finance and Membership.Lifecycle ProjectionCurrent state derived from lifecycle history.Relationship StateA user's relationship to an Entity, such as reading status or product preference.

For example:

Membership Account +40 Purchase -1 Class Session -1 Class Session +1 Correction Current remaining = 39

The current balance is a projection over ledger events.

21. Life Marks

Life Marks is intentionally not a second behavior database.

It is primarily:

Cross-domain Event Projection + Quick Entry Surface.

When a professional canonical event already exists, Life Marks queries or creates that domain event.

For example:

"Last painting session?" → Hobbies Session "Last oil painting class?" → Hobbies ClassSession

Only when no professional domain exists should Life Marks create a lightweight generic mark event.

This avoids duplicate life histories.

22. Home, Calendar, Search and Map

Home, Calendar, Search and Map are projection surfaces rather than canonical fact owners.

Home composes current life, future intent and resurfacing.

Calendar projects Events, Intents and connected external calendar references across time.

Search retrieves canonical objects, artifacts, evidence and authorized external references.

Map projects Places and geocoded life events.

They must not maintain duplicate canonical event stores.

This allows their UI and algorithms to evolve independently from the canonical personal history.

23. Composition and Narrative

Narrative presentation is separated from factual history.

A Plog may reference Event, Person, Place, Media, OOTD and Food facts without owning those facts.

Similarly, Travel Book, Garden Yearbook, Portfolio and Annual Review are Composition projects.

Canonical Life Facts ↓ Composition ↓ Render ↓ Image / PDF / Video / Dynamic Photo

The Composition remains editable.

Rendered exports are disposable outputs.

A Composition reference may be either live or snapshot-based.

A live reference follows canonical changes.

A snapshot reference preserves the presentation state at the time the composition was created.

This prevents later factual corrections from unexpectedly rearranging a manually authored scrapbook or portfolio.

24. Control Plane

Several cross-cutting decisions do not belong to individual business modules.

They form the Life OS Control Plane.

Permission / Capability │ Central Action Gate "May this action occur?" Central Attention Gate "Should the user be interrupted?" Work Scheduler / Resource Budget "Should this work run now?" System Health "Is the system itself operating safely?" Human-readable Audit "Who accessed or changed what?"

Modules submit requests to these systems.

They do not independently bypass them.

For example, Membership may emit an expiry candidate but does not independently decide to send a push notification.

25. Attention Architecture

Information that the user may want to know is not automatically a notification.

The Attention system distinguishes silent, ambient and interruptive delivery.

Attention Candidate ↓ Central Attention Gate │ ├── Ignore ├── Inbox ├── Home ├── Companion ├── Digest ├── Live Surface └── Push / Alarm

Examples of Live Surface implementations may include Android Live Updates or iOS Live Activities / Dynamic Island.

The same underlying activity can move between surfaces over its lifecycle.

A future concert may be silent weeks in advance, appear on Home on the day, become ambient near start time, and trigger a push only when the user explicitly requested such a reminder.

26. Work Scheduling

Background work does not execute merely because a worker has something to do.

OCR, embeddings, media backup, index rebuild, AI organization and other heavy tasks submit work to a central scheduler.

The scheduler considers user need, priority, network, charging state, battery, thermal condition and foreground activity.

The governing idea is:

Attention Gate decides who may disturb the user.

Work Scheduler decides who may disturb the device.

Expensive maintenance tasks should normally prefer Wi-Fi, charging and idle periods.

User-visible foreground requirements may run immediately.

27. Transactional Outbox

Canonical truth must not depend on fragile post-save callback chains.

A canonical domain transaction should atomically persist:

Canonical Mutation + ChangeSet + Post-commit Outbox Signal

Only then does the transaction commit.

After commit, a Post-Commit Processor may independently trigger:

Derived updates Sync replication Attention evaluation Cross-domain reactions

If any consumer fails, canonical truth remains committed and the consumer can retry.

This prevents the failure mode:

save() updateSearch() sync() notify() updateHome()

where process termination between steps silently loses required work.

28. Idempotency

Every asynchronous boundary assumes that work may be duplicated, interrupted or reordered.

Sync, Import, workers, background processing, attention delivery and domain reactions must therefore support idempotent application.

For example, consuming the same ClassSessionCreated signal multiple times must not deduct multiple membership lessons.

Effects should carry stable causal identity such as:

source_event_id effect_key

or equivalent idempotency keys.

The architecture assumes at-least-once delivery where appropriate and makes application safe to repeat.

29. Local-First Storage

Local persistence is the primary operational source for normal user interaction.

A normal save should mean:

Saved safely on this device.

It must not require immediate cloud availability.

Three states remain separate:

Saved ≠ Synced ≠ Backed Up

A local save succeeds first.

Sync later propagates accepted canonical changes to trusted devices.

Backup independently provides disaster recovery.

30. Sync

Synchronization does not replicate raw SQLite database files.

It replicates canonical state changes and media manifests.

Sync understands stable identity, revisions, schema versions, device origin and change-set identity.

Transport may repeat data.

Remote application must be idempotent.

Semantic conflicts must not be silently destroyed.

For example:

Phone: Concert 19:30 Tablet: Concert 20:00

is a semantic conflict.

Both values must survive until the system or user resolves them.

By contrast, one device adding a photo while another edits a non-conflicting caption may be automatically merged.

The synchronization architecture distinguishes:

Technical convergence

from:

Semantic correctness.

31. Revision and Patch Semantics

Canonical objects carry revisions.

Commands may state the revision against which they were prepared.

UpdateItemName( id, expected_revision = 17, new_name = ... )

If the canonical object has advanced to revision 18, the command must revalidate or enter conflict handling.

Older clients must use patch-like semantics for known fields rather than replacing entire objects.

This ensures unknown newer fields are preserved.

The governing rule is:

Patch what you understand; preserve what you do not.

32. Unknown Data Preservation

Older clients may encounter canonical objects, event types, fields or extension data they do not understand.

They must preserve such data.

They must not silently delete, normalize or down-convert it.

An older UI may display:

This record was created by a newer Life OS version. Update to view full details.

But Sync, Backup and Export must continue to preserve the unknown canonical payload.

Unknown does not mean invalid.

Unknown does not mean deletable.

33. Backup

Backup is separate from synchronization.

A backup represents a consistent recoverable state.

For SQLite-backed canonical data, a live database must not be naively copied while ignoring WAL state.

Backup must use a consistency-safe snapshot mechanism.

Recovery points should contain canonical state, schema metadata, essential recovery metadata and required media manifests or protected originals.

Regenerable Derived Data does not need to dominate backups.

Backup success should distinguish:

Job ran Snapshot created Snapshot verified

System Health should report the latest verified recovery point rather than merely the latest attempted backup.

34. Restore Epoch

Disaster restore changes the meaning of synchronization history.

If yesterday's snapshot is restored after today's bad changes have already reached the cloud, ordinary revision comparison must not immediately reapply those bad changes.

Therefore a disaster restore creates a new Recovery / Sync Epoch.

The restored state becomes an intentional new canonical baseline.

Sync must treat it as a user-authorized recovery operation rather than a stale device state.

This prevents the cloud from automatically undoing the recovery.

35. Media Architecture

MediaAsset is a shared canonical identity.

Modules do not copy original media merely because the same media appears in multiple views.

MediaAsset │ ├── system source reference ├── local/private locator ├── cloud original ├── metadata └── derived ├── micro thumbnail ├── preview ├── OCR └── embedding

Media identity is not the system URI, file path or file hash.

Those are locators or integrity evidence.

If one locator fails, the MediaAsset may remain valid through another source or cloud backup.

Media backup and binary transfer have their own lifecycle and must tolerate partial success, retry and orphan cleanup.

36. Creative Vault Boundary

Creative Vault is not implemented as an ordinary Life OS record with a private=true property.

It is a separate security domain.

It has an independent encrypted local boundary, independent sync encryption, independent search and independent lock/recovery behavior.

Ordinary Life OS and ordinary AI systems must not observe:

Vault titles Vault object IDs Vault metadata Vault relations Vault embeddings Vault event hooks Vault search results Vault share history

There are no canonical references from the normal Life OS world into private Vault objects.

If the user explicitly exports something from Creative Vault, the result becomes a new ordinary artifact outside the Vault.

This preserves Vault non-observability.
