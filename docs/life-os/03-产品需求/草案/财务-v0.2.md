## 1. 用户明确需求

### 1.1 账户真实流水与个人收入/消费分开

- 钱具体从哪个账户流出、流入哪个账户都要完整保留。例如银行卡 A 付款 ¥215，之后返利进入支付宝，好评返现进入微信；原付款不能改成一个折后净额。
- “个人实际消费”“个人实际收入”“商品最终成本”是对真实流水及业务关系的解释和计算，不能与账户流入/流出混为一个金额。
- 同一件事可以关联不同日期、不同账户的多笔流水。

### 1.2 每次发现财务场景，立即弹窗复核，再正式记账

- 用户喜欢过去记账软件的自动场景识别和即时弹窗，不喜欢事后逐笔手填，也不希望静默自动入账。
- 用户侧流程应为：**支付/转账/订单场景被识别 → 立即弹出预填复核窗口 → 用户检查或修改 → 点击确认 → 才正式记录**。
- “候选”可以是系统内部识别状态，但不应把“先进入候选箱、以后处理”当成主要交互。未经确认的候选不属于正式账本。
- 普通支付应尽可能一眼确认；复杂电商优惠场景可借助悬浮球识别当前页面，展开更多字段复核。
- 必须重视识别准确性，不能把 OCR / 自动推断直接当成用户已确认的财务事实。

### 1.3 正式记录需要具体的商品或服务明细

- 不满足于“早餐 ¥18 / 分类餐饮”，应记录具体吃了什么，例如豆浆、油条等，条件允许时保留数量、单价和金额。
- 购物订单应保留每件商品/服务明细，而不是只存“淘宝 ¥327”。一个订单里的不同商品可以分别关联护肤、Closet、Garden、Items 等领域。
- 如果一条记录不涉及购物商品，例如转账或报销，也应记录清楚其具体事由/所对应的事情，而不只是一个笼统类别。
- 食物明细应与 Food / Plog 的早餐、午餐等生活事件建立关联；不是让两个模块重复创建独立的“同一顿早餐”。

### 1.4 已知的业务性质要在首次付款复核时确定

- 用户通常在付款时就知道这笔钱是不是分账、代拍、报销等；首次复核时应可选业务性质并建立后续关联基础。
- 业务性质与消费分类不同。例如“餐饮”是分类，“分账”是该笔付款的业务性质。
- 分账的目标是正确整理自己的花费及各账户资金流，不需要催款式 AA 软件。用户有时是自己忘记通知朋友付款，并非必须跟踪谁有没有还钱。
- 朋友可能分别转到微信、支付宝，且比原付款晚几天；原银行卡付款和后续转入都真实保留，事后关联到同一件事。
- 代拍的付款、朋友转款、支付优惠、后续返利可能分布在不同账户；不计为普通个人支出/收入，但应能算出一次代拍最终赚/亏多少钱。用户不强求差额一定归类为传统“收入”。
- 报销的垫付款不计入个人消费，报销款不计为个人收入；账户真实流水仍保留。

### 1.5 延迟到账关系分为“当场已知”和“发生后才知道”

- 分账、代拍、报销等通常在原交易确认时就知道未来可能有对应转入，应当场建立事件和预期关系。
- 好评返现、部分返利等有时是否到账、何时到账和具体金额并不确定，不应在原订单中伪造确定流水。
- 后续真实到账时，系统应利用原订单及业务信息提出相关候选，并在弹窗中让用户确认关联；不能突然拿一笔没有上下文的一个月前收入让用户回忆。
- 一次付款可能对应多次返利或退款；一次结算也可能涉及多件事情。不能将关系模型限制为两个流水 ID 的简单一对一配对。
- 未经用户确认的“来源不明的流水”不应悄悄进入正式账本。

### 1.6 退款、返利与付款不能互相覆盖

- 退款是实际到账的独立账户流水，可能与付款账户不同；退款后对应购买的最终个人消费应相应减少。
- 返利、好评返现同理：保留到账账户和发生时间，同时更新关联事件的成本计算。
- 订单/商品优惠应保留明细，包括店铺优惠、平台优惠、满减、支付优惠、会员优惠、返利、好评返现等；不能只剩下最终实付数字。

### 1.7 储值的个人记账口径

- 用户认为不可自由提现的储值充值当下已构成自己的消费。
- “充 ¥100 得 ¥120”要同时表达：真实付款 ¥100、个人消费 ¥100、卡内可用价值 ¥120、赠送价值 ¥20。
- 以后用卡内余额购买东西，卡内消耗需要记录，但不应再次把 ¥120 算作新增加的个人现金支出。
- 卡内购买的商品是什么、面值多少、如何衡量商品真实成本，与充值时已记支出的关系仍有细节待第二轮或 Membership 讨论，不擅自冻结分摊规则。

### 1.8 财务与会员管理分开、数据关联

- Finance 负责何时支付、在哪个账户支付、对应什么业务以及花了多少钱。
- Membership / Balance 的独立界面负责卡内剩余余额、赠送额度、会员期限、到期、续费等管理；会员卡消费仍要在账本里体现，但不能造成个人支出重复计算。
- 用户关注余额和到期，不要求重点追踪影视会员等的使用频率。

### 1.9 生活语境、购物活动及跨模块统计

- 可以给花费添加“回家交通”等有意义的标签，回答本月/今年回家几次、每次多少钱、总交通费用多少；不只看大类“交通”。
- 应支持按双11、618 等购物活动汇总：**买了什么商品、各买多少、总共花多少钱、哪些是好价/神价、优惠和返利多少**。
- 保留原有商品价格研究习惯：购入价、数量、单位、单位价格、原价、活动促销、好价/神价、各种优惠及后续收益等丰富字段；不能因为界面要简单就删除底层信息。
- 用户关心月度真实消费、分类/领域花费、园艺开销、回家费用、优惠与返利节省、代拍赚/亏、未用储值、即将到期余额、大额消费及具体商品最终成本。

### 1.10 视觉与入口偏好

- 重点参考用户提供的“纸质小票/日常收据”视觉。
- 记录确认首选**只覆盖下半屏的小票式弹窗**，简单账少量字段直接确认，复杂订单再展开明细。
- 用户希望尽量有系统级快捷入口，特别期待研究与 vivo 灵动岛/原子岛或类似能力结合。
- 系统能力是否对第三方开放及设备适配尚未验证；不能在需求阶段当作已实现能力。

## 2. 用户偏好

- **数据极繁，界面克制。** 明细、价格、优惠和关系都可以丰富，但常见场景的操作必须轻。
- 优先系统主动发现，而不是用户主动回到 App 补账。
- 对真实性与可复核性要求高；省步骤不等于允许系统无确认地写入。
- 财务应反映钱与实际生活的关系，不只是传统收支饼图。
- 不需要传统催债管理，也不想被频繁、无上下文地要求回忆旧账。

## 3. AI 当前理解 / 建议（未确认的设计方案）

- 分离概念：账户流水、财务事件、订单、订单明细、优惠、业务归属、生活事件与统计视图；具体实体与表结构待架构设计。
- 一张订单小票可以关联多件商品，每件商品可连接不同领域；一个生活事件也可关联多笔付款，不重复创建经济事实。
- 识别后尽快弹出半屏确认；窗口中默认展示高度可靠且必要的信息，用户主动展开优惠、详细业务归属、证据及多商品明细。
- 已知分账/代拍/报销在首次确认时建立事件骨架；后续转账匹配优先利用这种既有上下文。
- 对无明确关联的到账候选，不给出强行猜测，更不能写成已经确定的返利。
- 对整单优惠，原始归属与用于分析的计算分摊应区分，避免把推算结果伪装成平台明示的逐商品优惠。
- 商品的“好价/神价”可通过用户定义阈值、历史购买与单位价格辅助判断，但定义、自动判定和用户确认规则留给 Shopping / Price 模块讨论。

## 4. 真实使用场景

### 4.1 早餐与 Food / Plog

微信支付 ¥18 → 系统识别 → 半屏小票预填商户、时间、账户、豆浆/油条等实际明细 → 用户检查并确认。Food / Plog 引用同一早餐事件，后续可添加照片、评价和感受。

### 4.2 跨账户分账

银行卡 A 支付聚餐 ¥300，初次确认标记为分账，个人承担 ¥100、他人承担 ¥200。第二天微信 +¥100、几天后支付宝 +¥100；分别弹窗，利用既有分账事件提出关联，用户确认。最终该聚餐个人消费 ¥100，原始三笔流水均保留。

### 4.3 代拍存在优惠和收益

银行卡实际支付 ¥775，朋友微信转入 ¥780，支付宝以后返利 ¥10。三笔账户流水属于同一代拍事件，个人普通消费/收入不因这些往来虚增，事件净差额可查询。

### 4.4 报销

银行卡支付出差费用，初次确认标记可报销，之后收到公司报销。两笔账户流水存在，但在用户个人收入和消费统计口径中均不计入。

### 4.5 退款到另一账户

购物时银行卡付款 ¥500，之后支付宝部分退款 ¥180。保留两条账户流水，对应订单最终成本据关联关系更新。

### 4.6 双11 多商品订单

同一订单包含护肤品、T 恤和园艺肥料，附带店铺券、满减、88VIP、红包、支付优惠及可能的后续返利。复核时保存商品与订单优惠层级，关联双11活动。之后活动专题可按商品明细展示买了什么、花了多少、好价/神价及后续实际成本。

### 4.7 储值卡

银行卡充 ¥100 得 ¥120，在 Finance 记录充值当下真实支出 ¥100；Membership 展示可用 ¥120 和赠送价值。后续卡内扣款是余额消耗，不再次作为一笔新个人现金支出。

## 5. 用户不想要什么

- 未确认就自动正式入账。
- 识别后只进入候选箱，期待用户以后再想起来处理。
- 来历不明的旧流水突然被要求回忆和匹配。
- “早餐 ¥18”这种只有金额和分类、没有实际买了什么的记录。
- 为了统计而改写银行卡/微信/支付宝原始出入金额。
- 把报销、代拍、分账归还粗暴当成普通收入/支出。
- 储值充值和卡内消耗重复算成两次个人支出。
- 一张订单跨多个领域时，分别复制多份独立购买事实。
- 把所有会员余额和有效期管理塞进 Finance。

## 6. 核心对象（概念层；命名未冻结）

- 真实账户与账户流水
- 财务事件 / 业务性质
- 订单与商品/服务明细
- 优惠、折扣、返利和退款
- 用户确认及原始证据
- 分账、代拍、报销的事件关系
- 生活事件/语境标签
- 购物活动（例如 2026 双11）
- 个人消费/收入与最终成本的计算视图
- 储值/会员的跨领域引用

## 7. 核心动作

- 场景发现后即时弹出复核
- 检查/修改账户、金额、明细与事由
- 选择自己消费、分账、代拍、可报销、储值、转账等业务性质
- 根据业务性质填写最少必要信息
- 确认正式记账
- 后续到账时确认关联原事件
- 对订单添加商品、活动、优惠与标签
- 查看真实流水、个人消费、订单成本和活动统计
- 从 Finance 跳转到 Food、Plog、Items、Closet、Garden、Membership 等相关内容

## 8. 最小记录成本

- 普通场景：自动预填完整且可验证的信息，半屏一眼复核，点击确认。
- 复杂购物场景：先显示概要，按需展开商品/优惠/业务详情。
- 无法识别商品明细时：不能编造；应提供快速补充具体内容的方式，是否允许先确认仅部分明细待第二轮明确。

## 9. 自动化边界

**已确认：** 自动发现和预填是重点；每笔正式流水需用户复核确认；已知业务性质在第一次复核时确定；后续到账通过已知事件上下文匹配；OCR/AI 推断不能直接冒充真实事实。

**待技术验证：** Android 不同支付 App/系统对通知、悬浮窗、页面识别、后台监听、vivo 系统入口等的实际授权与可用性；这些能力不得在技术评估前当作承诺。

## 10. 与其他模块的关系

- **Capture：** 识别页面/通知/截图/小票、悬浮球与即时复核入口。
- **Items / Shopping / Price：** 商品身份、购入数量、单位价、好价/神价、历史成本。
- **Closet / Skincare / Garden：** 订单明细与具体领域物品或耗材关联。
- **Food / Plog：** 食物购买和实际早餐/午餐等生活事件相互引用。
- **Travel / 回家：** 按生活语境聚合交通、住宿等花费。
- **Membership / Balance：** 充值付款、卡内可用额度、赠送价值、余额扣减、期限/续费分别归属对应领域且相互关联。
- **Home：** 仅展示经用户允许的轻量财务摘要。

## 11. Home Surface（DRAFT）

- Finance 属于敏感数据，不默认把详细账户余额、逐笔流水或收入展示在日常封面。
- 候选信息：用户开启时，可展示某生活主题花费、双11专题摘要或余额即将到期的轻提示。
- Home 展示许可与导出分享许可相互独立。
- 具体内容、频率、隐私等级和展示形式尚未确认。

## 12. 模块内部信息层级（待第二轮）

待讨论：日常账本、账户流水、消费事件/订单明细、购物活动、分类/标签统计、优惠返利、已关联后续款项与跨域入口的布局。不能用当前代码导航作为最终产品要求。

## 13. 导航 / 入口

- Finance 有独立领域入口；日常记录主要依靠外部场景自动发现后的半屏确认，不应要求先打开 Finance。
- 辅助入口可包括悬浮球、系统分享、快捷操作、通知或经技术验证可用的 vivo 原子岛/类似系统能力。
- 用户明确偏好小票式下半屏弹窗，不希望普通场景强制整屏跳转。

## 14. 搜索 / Capture / 快捷操作

支持以商品、账户、业务性质、生活标签、购物活动及时间查询，例如：

- “双11我买了什么、花了多少？哪些是神价/好价？”
- “这个月回家交通花了多少？回家几次？”
- “这件衣服返利回来以后最终多少钱？”
- “今年园艺花了多少钱？”
- “这次代拍最后赚/亏了多少？”

## 15. 隐私与 AI 权限

财务属敏感领域。AI Partner 可访问的细节层级、是否允许跨账户明细、哪些数据可进入 Home 或导出，都需要用户后续明确决定。不得根据产品便利性默认扩权。

## 16. Media

可引用订单截图、小票、支付凭证、商品图片和已有照片；原始证据与机器识别结果分离；跨模块引用统一媒体身份，避免重复复制。

## 17. 分享 / 导出

未来可生成个人保存的消费报告、购物活动清单及按范围选择的脱敏统计；默认不公开详细账户和财务隐私。具体格式与权限待确认。

## 18. 明确不做

- 不做以催债为核心的传统 AA 软件。
- 不把所有财务关系压缩为单一的“收入/支出 + amount”。
- 不默认静默自动正式入账。
- 不以未知流水事后清理为主要工作流。
- 不在 Finance 中复制其他领域的数据或取代 Membership 管理页。
- 不为了首页好看而牺牲订单/商品的详细数据。

## 19. MVP（AI 建议；未确认）

- 支付场景检测后半屏复核原型（能否跨 App 即时触发须技术验证）。
- 真实账户流水和用户确认记录。
- 订单/商品或服务明细。
- 业务性质及分账、代拍、报销的最小关系。
- 退款/返利等后续到账关联。
- 生活语境标签、双11等购物活动聚合。
- 与 Items、Food/Plog、Membership 等领域的最小可追溯关联。
- 不同统计口径分离，避免重复计算。

## 20. 验收标准（需求层）

1. 系统不能在用户未确认时把识别到的付款写成正式账单。
2. 正常场景下能立即展示预填的下半屏复核窗，操作显著少于逐笔手填；实际跨 App 可用范围另做设备验收。
3. 同一笔订单可以留存商品/服务明细、优惠及支付账户；不同商品可关联不同领域。
4. 一笔银行卡付款和多笔不同账户的后续转入可归属同一财务事件，原始流水不变。
5. 报销、代拍、分账返还不会污染个人普通收入或消费统计。
6. 退款与后续返利可关联旧订单并更新成本视图，但不能伪造原始款项。
7. 充值与后续卡内扣减不会重复计入个人消费。
8. 能查看某年双11购入商品、支付额、折扣/返利与好价/神价标记。
9. Food / Plog 等领域可使用同一生活事件/购买明细，不需重复录入另一份事实。

## 22. 已被后续推翻

- **“检测后先放候选箱，以后处理”作为主要交互** → 改为检测后立即弹窗，用户确认才正式入账。
- **“来源不明的流水先正式记下，以后再关联”** → 用户不接受无上下文的未知正式流水；首次付款就应建立已知业务性质，后续到账利用事件上下文匹配。
- **“只记金额和大类即可”** → 用户需要每笔消费具体商品/服务明细，并与生活领域关联。
- **“充值只是账户之间转移，不算个人消费”** → 与用户对不可自由提现储值的个人账本口径不符。
- **“分账必须追踪欠款并催收”** → 不是用户需求，重点是跨账户归集及正确统计。
