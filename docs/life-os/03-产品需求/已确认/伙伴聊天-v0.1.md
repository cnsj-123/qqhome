# Life OS — Companion Chat / AI 聊天前端 PRD v0.1 FINAL

**状态：CONFIRMED（核心需求）；开源竞品深调与具体技术接口待后续阶段**  
**定位：Life OS 内与 Companion AI 长期相处的聊天空间；以交流为中心，工具能力作为按需调用的后台扩展。**

## 1. 核心定位

Life OS 不只是生活记录应用，也提供用户与 Companion AI 自然相处的界面。

目标是：

> 一个像微信聊天一样亲切、可持续、历史不丢的 AI 对话区。

它不是把 Operit 式强工具工作台直接嵌入生活首页，也不是让 AI 成为要求用户完成任务的管家。

## 2. 入口与导航

- Life OS 打开后仍首先呈现 Home / Today Scrapbook。
- 从 Home 向上滑可进入 Companion Chat。
- 返回 Home 后，主聊天及其历史继续存在。
- 具体手势冲突、动效和可发现性在 UI 原型阶段验证。

首版不需要复杂代理工作台入口。

## 3. 会话结构

- **持续的主聊天**：日常交流默认进入同一个长期延续的对话。
- **可另开会话**：讨论专题、短期问题或其他明确话题时允许新建会话。
- 主聊天不因另开专题而被覆盖。
- 不强制用户每次选择项目、角色或工作区。

## 4. 历史记录持久化

聊天前端必须保存完整历史，而不是依赖模型上下文或长期记忆摘要来“还原”聊天。

至少保留：

- 会话标识与消息顺序。
- 用户和 AI 的完整消息内容。
- 消息发送时间。
- 用户主动发送的附件引用。
- 从 Life OS 明确分享的记录卡片及其必要展示信息。
- 消息的发送/生成状态，避免网络中断后出现不明结果。

需要支持浏览历史；跨设备恢复、备份、导出与同步方式在全局 Media/Sync/Chat 架构阶段设计。用户未主动删除前不应因自动摘要或模型上下文窗口变化而丢失原始聊天。

## 5. 聊天历史 ≠ AI 长期记忆

三个系统职责不同：

- **聊天前端**：保存真实、完整的对话历史与消息附件。
- **独立记忆系统**：保存长期记忆，负责相应记忆形成、检索、演化与遗忘机制。
- **Gateway**：编排上下文、记忆注入、模型调用与缓存策略。

网关可选择部分历史和相关记忆作为本次请求上下文，但前端不能因为模型没有收到全部旧消息就删除历史。

前端不另造一套与既有记忆系统竞争的长期记忆数据库。

## 6. 请求链路

逻辑链路：

1. 用户在 Life OS 聊天前端发送消息。
2. 前端持久保存用户消息及明确附带的材料。
3. 请求经 Gateway 处理。
4. Gateway 按隐私授权选择上下文、记忆和模型。
5. Companion AI 返回回复。
6. 前端展示并保存完整回复。

具体传输协议、断线恢复、幂等消息 ID 和安全策略在技术架构阶段确认。

## 7. 发送 Life OS 内部记录

用户可以在普通模块中选择“发送给 AI”，进入聊天并形成类似微信分享卡片的记录。

例如：

- Food：某次吃饭体验。
- Travel：某次旅行。
- Shopping：某项购买记录。
- Garden：某株植物。
- Knowledge：某条收藏或整理稿。

用户可以附加一句话或继续讨论。

分享只代表用户明确选择的该记录及其授权范围，不自动授予整个模块读取权限。发送的卡片应有明确来源与可追溯的内部对象引用。

## 8. 系统外材料

聊天输入区支持用户主动发送系统外材料，例如：

- 文字。
- 图片。
- 文件。
- 链接。

具体视频、音频、文件格式、大小限制和上传策略在 Media 与技术阶段确认。

## 9. Creative Vault 禁区

- Creative Vault 不出现“直接发送给 AI”的功能入口。
- AI 不能直接浏览、搜索或索引 Vault。
- 不能因为用户在普通聊天里提到某个创作概念，就自动获取相关 Vault 内容。
- 若用户主动自己描述一部分创作内容，那只属于这次用户实际发送的聊天文本，不构成开放 Vault 权限。

## 10. 首版交互风格

优先：

- 清楚的消息气泡。
- 舒适的长对话浏览。
- 附件与分享卡片。
- 持续主聊天与新会话。
- 消息状态、失败重试与历史定位。

不把工具日志、工作区树、终端、任务看板、Agent 控制台作为主界面的常驻元素。

## 11. 工具弱呈现，能力可扩展

用户希望工具性弱，指的是**对话呈现应以陪伴为主**，并非要求牺牲未来的底层扩展能力。

设计原则：

- 默认聊天为主。
- 按需调用被授权的工具。
- 使用工具时不必把全部技术流程灌进聊天内容。
- 有副作用的操作必须明确告知并遵循确认流程。
- 必要执行信息可按需展开。
- 未来增添购物、音乐、搜索或其他功能时，应通过可配置能力接口扩展，不改写聊天历史存储模型。

首版不开发全设备自动化或复杂 Agent 工作台。

## 12. Operit 作为参考，而非照搬

用户当前使用 Operit，并希望研究其成熟前端设计，但让 Life OS 的工具性更弱。

后续正式开源调研重点：

- Android 聊天交互。
- 主会话与多会话。
- 聊天历史、备份与恢复。
- 附件处理。
- 多模型 / 多 API 接入。
- 工具权限与操作透明度。
- 前端可扩展接口。

Operit 中的复杂自动化、终端、项目工作区及多工具工作台，仅作为架构参考，不属于首版默认交互需求。

参考仓库：<https://github.com/AAswordman/Operit>

## 13. 与后台多模型的关系

Life OS 允许不同模型承担：

- OCR。
- 图片识别。
- 知识整理。
- 向量检索。
- 聊天。

Companion AI 是主要对话角色。后台工作模型不需要以独立聊天角色出现，也不需要获得用户全部长期关系上下文。

## 14. 权限与审计

所有数据读取、外部工具调用和正式数据修改都受 Privacy & AI Permissions 约束。

聊天前端可以呈现授权弹窗，并应使用户能查看必要的操作信息，但不代替网关/服务端的实际权限执行。

AI Search 的启用开关是搜索功能设置，不等于为整个聊天永久开放所有数据。

## 15. Home 与整体体验

Home 仍是进入 App 的首页；聊天通过上滑进入，形成生活记录与 Companion 交流之间自然切换。

AI 的角色是伙伴，不是催促式管理者。不能因为 Life OS 接入很多模块，就默认在每次对话中检索、分析和安排用户的生活。

## 16. 首版明确范围

首版需要：

- 持续主聊天。
- 可另开会话。
- 持久化完整历史。
- 清楚的聊天消息与基本状态。
- 普通 Life OS 记录卡片分享。
- 系统外文字、图片、文件及链接入口。
- 接入现有 Gateway / Memory System 的明确边界。
- 按权限提供少量必要能力。

首版不需要：

- 自动购物。
- 听音乐 / 媒体控制工具。
- 全设备 GUI 自动化。
- 终端与开发工作台。
- 多 Agent 任务编排 UI。
- 把所有工具暴露为聊天常驻按钮。

## 17. 后续待架构/竞品调研确认

- Android 手势与聊天 UI 原型。
- 完整历史的同步、备份、导出与恢复。
- 附件在聊天前端、Media 和 Gateway 间的传输契约。
- 上下文裁剪、缓存与网关请求格式。
- 断网、消息重试和流式中断处理。
- 多模型服务的配置与秘密凭证存储。
- 消息分支、搜索、引用与长对话定位是否纳入首版。
- Operit、Open WebUI、LibreChat、SillyTavern 的具体可借鉴设计与代码许可。

**本 PRD 确认产品需求；不代表底层扩展与同步技术已经实现。**
