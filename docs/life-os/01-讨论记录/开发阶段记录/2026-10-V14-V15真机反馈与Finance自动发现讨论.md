### 现在真正需要修的 3 个地方

**第一，所有银行被压成一个 `BANK`，这会严重影响以后真正的自动化。**

现在：

```text
工商银行 App ┐
建设银行 App ├→ FinanceSource.BANK
招商银行 App ┤
农业银行 App ┘
```

短信也是：

```text
95588
95533
95555
...
↓
FinanceSource.BANK_SMS
```

于是系统知道：

> “这是银行提醒”

但不知道：

> “这是工商银行”  
> “这是建设银行”  
> “这是招商银行”

这意味着以后规则根本没办法很可靠地做：

```text
工商银行动账 → 工资卡
建设银行动账 → 建行卡
招商银行动账 → 招商信用卡
```

现在 merchant/bank proposal 也特意不自动绑定账户，所以最后你还是要手选。

我不建议搞 20 多个 `FinanceSource.ICBC / CCB / ABC...`，会越来越脏。更合理的是保留：

```text
source = BANK
channel = NOTIFICATION / SMS / SCREEN
origin / institution = ICBC / CCB / CMB / ...
```

也就是说：

**来源类型和具体机构身份分开。**

这个才适合以后扩银行。

---

**第二，现在银行短信/银行通知的原文会真正进入持久化 Proposal。**

这一点我认为比 UI 更重要。

屏幕识别这部分反而做得很好，它最后只留下类似：

```text
支付成功
¥23.45
交易单号：...
```

不会保存整屏。

但 `FinancePaymentEvidence.inspect()` 处理通知和银行短信时现在直接：

```kotlin
evidenceText = text.take(1800)
```

所以一条银行短信如果包含：

```text
尾号
余额
商户
交易时间
金额
```

这些内容都有可能跟 Proposal 一起存进 Room。

而我们 Finance backup 本来就会备份 Proposal；这个 patch 甚至专门新增了“新来源可以随 V4 Backup round-trip”的测试。

所以：

> 诊断页不保存原文 ✅  
> 但正式 Proposal 仍可能长期保存银行短信原文 ❌

以前微信/支付宝就已经有这个倾向，但扩展到银行短信后敏感程度明显上升。

我建议改成：

```text
原始通知/SMS
↓ 只在内存解析
提取
- 来源
- 银行身份
- 收支方向
- 金额
- 明确交易号（如果有）
- 必要的脱敏商户/说明
↓
Proposal evidence 保存“最小证据”
```

不要长期保存完整银行短信。


理论上都可能进来。

现在代码只有在**明确交易单号完全相同**时才真正去重，而且 BANK / BANK_SMS 还特意不参与 transaction-ID 自动去重。

金额相同、两分钟内发生的记录只会显示：

> “可能是同一笔交易的不同提示”

然后仍然保留多条 Proposal。

这个策略比“瞎合并”安全，我认可。

但一旦你把来源开这么多，它很容易变得非常吵。

所以后面最好不是：

```text
4 条 Proposal
```

而是：

```text
一个待确认交易候选

依据：
支付宝通知
淘宝结果页
工商银行通知
工商银行短信
```

也就是：

> **Proposal 是待确认的交易候选，Evidence 可以是多份。**

只有明确交易 ID 才自动合并；金额+时间只做“建议归为同一组”，不能偷偷认定是同一笔。

这个会比现在的“出现 4 条然后让用户逐条忽略”高级很多。

### 关于无障碍和短信权限，还有一个发布问题

如果以后只是你自己装 APK，这个问题不大。

但如果以后真想放 Google Play，这两个属于需要提前考虑的东西。

Google Play 对非无障碍工具使用 AccessibilityService 要求**单独、醒目的应用内披露 + 用户明确同意 + Play Console 声明**。你现在 patch 里的“开启屏幕支付识别？”弹窗是正确方向，而且 `isAccessibilityTool=false` 也是诚实的。[Google 帮助](https://support.google.com/googleplay/android-developer/answer/10964491?hl=en-en\&utm_source=chatgpt.com)

SMS 权限也属于受限权限；好消息是 Google Play 明确把“**基于短信的资金管理，例如预算跟踪/管理**”列为可能允许的场景之一，不过需要申报并接受审核。[Google 帮助](https://support.google.com/googleplay/android-developer/answer/17225965?hl=zh-Hans\&utm_source=chatgpt.com)

所以以后如果考虑商店发行，我甚至倾向做：

```text
Life OS Store build
通知自动发现为主
高敏感能力按商店规则控制

Life OS Full / self-host build
通知 + SMS + Accessibility
```

现在先不用做 flavor，但架构上不要把这些能力绑死。

### 还有一点：目前并不是“各种支付软件都支持了”

现在已经覆盖一批主流来源，但代码里还没有列：

```text
拼多多
饿了么
滴滴
抖音 / 抖音商城
快手
小红书
携程 / 去哪儿
唯品会
苏宁
……
```

不过我**不建议现在无脑继续堆 package name**。

真正决定成功率的不是：

> “我们索引了 50 个 App 名字”

而是：

> “我们有没有这个 App 的真实支付完成通知 / 支付结果页样本，并且有对应 parser fixture。”

尤其淘宝、京东、美团这种 App 很多通知其实是：

```text
订单发货
优惠券
商品降价
商家接单
物流
```

不是支付。

当前 parser 有要求“明确完成信号”，这点是对的。不要为了支持率把它放宽成“看到金额就记账”。

所以我的当前判定是：

```text
多来源架构                   ✅

SMS → Proposal               ✅
Accessibility → Proposal     ✅

银行机构身份                  ⚠️ 需要补
原始银行证据最小化            ⚠️ 需要补
跨通道证据聚合                ⚠️ 很快会需要
真实来源覆盖                  ⚠️ 不能只靠 package list
```

**我现在最不希望 Codex 做的，就是继续一口气再加 30 个 App。**

先把“来源类型 / 具体机构 / 采集通道 / Evidence / Proposal”这几个概念分干净。否则现在只是 10 个来源还好，以后 50 个 App × 通知 × SMS × 无障碍，很快会变成自动记账屎山。
